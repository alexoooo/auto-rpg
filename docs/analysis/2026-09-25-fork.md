# A forkable world: isolation, divergence, ranking and cost

2026-09-25. Skill ceiling session 02 (`docs/plans/2026-09-25-skill-ceiling-02-fork.md`). Every
figure is Node and headless, measured on main at release-120 (5ac61ce: 120 Hz physics and control,
`solverTuningHz` 240, contacts read on arrival), and names its harness. "Node bout runner" means
`tests/harness/bout-runner.mjs` with the fork harness beside it (`tests/harness/fork.mjs`). "Fork
study" means `research/fork-study.mjs`, which runs on that harness in six worker lanes, one job at a
time per lane.

**Answer.**

- **Isolation is bit-identical.** A bout that has forks built, stepped and discarded throughout is
  the same bout to the bit as one with none. That holds whether the forks share its Havok instance
  or not, so the worker fallback is not needed.
- **There are two kinds of fork, and the exact one is exact.**
  - A *teleport* fork writes the state through Havok's getters and setters. It starts with the
    solver's memory cold.
  - An *exact* fork copies Havok's whole linear memory (16.9 MB) into a fresh instance holding a
    world built by the same code. It is the original to the bit: pose, bout result and state graph
    agree for as long as both run. That holds after a sever and with a maul's mid-bout grip.
- **The exact fork is the planning substrate.** Over 222 fork moments it ranks four command prefixes
  exactly as a replay from t = 0 does, at every horizon: 222 of 222 score vectors are identical.
- **The teleport fork is not.** It agrees on 74.3 % of prefix pairs at 1 s and picks the same best
  prefix 58.2 % of the time. It is still well above chance at 0.5 s (82 %).
  - The cause is not missing state. A 7 mm start grows to a 0.67 m tip gap (p90) within a second, so
    a bout is chaotic at the scale a planner cares about.
- **The opponent's dice barely matter over one second** (exact fork, opponent reseeded): 221 of 222
  score vectors are unchanged at 1 s and 201 of 222 at 2 s. The probe minds rarely draw.
- **Cost, one lane on a busy host.**

  | step | median |
  |---|---:|
  | capture, heap included | 26 ms |
  | exact fork, fresh instance included | 93 ms |
  | one simulated second of a fork | 222 ms |

  A simulated second costs what it costs the original (243 ms).
- **Gates.**
  - Isolation: **passes.**
  - Ranking at 1 s: the threshold, set below from the data, is pairwise agreement ≥ 0.98 and top-1
    ≥ 0.95. The exact fork **passes** (1.000 and 1.000). The teleport fork fails.
  - Neither fork ranks at chance at 0.5 s.

## 1. The interface

`src/forkable.ts` defines one interface, and the fork calls it without asking what a piece is:

```ts
interface Forkable {
  captureState(): Record<string, unknown>;
  restoreState(state: Record<string, unknown>): void;
  prepareState?(state: Record<string, unknown>): void; // a piece that builds part of itself lazily
}
interface Topological { captureTopology(): unknown; restoreTopology(topology: unknown): void; }
```

**Which pieces implement it.**

- **Classes** implement nothing. The walk (`src/fork/graph.ts`) captures every own data field,
  non-enumerable ones included, and pairs objects by path. So a field added to `Combat`, a `Golem`
  or the recorder is forked the day it is added.
- **Closures** hand over their `let`s and privately held objects through `captureState`. That
  covers every golem module, carrier, pilot, tactic and style director, and every named golem mind.
  A `let` that need not be forked says why on its declaration line: `// fork: derived`, `config`,
  `presentation` or `instrument`. Ten lines in `src/` carry one.
- **`mulberry32`** is itself `Forkable`, and has a `reseed`.
- **A body that loses parts** is `Topological`. The fork replays its severs, ruins and maul grips on
  the fresh body before any field is written, because those dispose joints and re-layer shapes.

**The restore order** (`src/fork/world.ts`):

1. Topology.
2. The JavaScript graph, from the bout's roots: runner, both bodies, both `Combat`s, the recorder.
3. Havok (`src/fork/native.ts`).
   - A teleport fork writes every body, shape, joint axis and the physics accumulator through
     Havok's own getters and setters.
   - An exact fork first copies the captured heap over the fork's instance. Every native write after
     that finds its value already there and is skipped.

A mind is snapshotted, restored and reseeded on its own through `src/fork/mind.ts`, for a planner
that asks "what would this mind do from here".

**The completeness check.** `tests/harness/closure-audit.mjs` opens every live closure's scopes
through the inspector (`[[Scopes]]`). It names every `let` and private object that no record hands
over and no exemption covers.

`tests/fork.test.mjs` runs it over:

- three pairs of builds that between them field every chain, every terminal, and every locomotion,
  trunk and head on the registry, human and skeleton builds included;
- every named golem mind.

It asserts that coverage against `EFFECTOR_CHAINS`, `EFFECTOR_TERMINALS` and `GOLEM_MODULES`, so a
module added to the registry and left out of the builds fails the test too. A synthetic control shows
the audit finding a missing `let`.

**The minds covered** are `idle`, `golem-duelist`, `golem-miser`, `golem-researched-needle-v1`,
`golem-champion` and `golem-brawler`, plus the styles and tactics they are made of.

**Not covered:**

- `pairedMind` and `adaptiveMind` in `lab-bespoke.ts`;
- the network and terminal-model lab minds;
- the human and skeleton policies.

A fork of a bout that uses one of these carries only what the walk reaches. Run the audit on the mind
before trusting it.

**A write of the value already there is not a no-op in Havok.** Measured in place on an exact replay
(Node bout runner, brawler against miser, frame 240, three frames on), rewriting each property to its
own value moved the world by:

| property rewritten to its own value | largest part moved |
|---|---:|
| body mass properties | 3.21 mm |
| body transform (QTransform) | 5.32 mm |
| axis motor stiffness, axis motor velocity target | 0.18 mm |
| every other body, shape, joint and axis property | 0.00000 mm |

So the restore writes only what differs (`writeIfChanged`). With that, a capture restored over the
world it came from leaves the world bit-identical with a twin nobody touched
(`a_capture_restored_over_the_same_world_changes_nothing`). Removing the check turns that test red
at frame 1.

## 2. Isolation

Node bout runner. Each case compares the bout's pose bytes on every frame, and its result, with the
same bout and seeds run without forks.

| original | forks taken | forks built into | verdict |
|---|---|---|---|
| brawler v champion, 240 frames | at 40, 100, 170, each stepped 1 s | the original's instance | bit-identical (test) |
| odd build (three legs and one arm, against a wheeled head-rammer), 150 frames | at 30, 75, 120 | the original's instance | bit-identical (test) |
| brawler v miser, 720 frames | throughout | the original's instance, and a second one | bit-identical; hash 00eb82f73f2fef76, damage 2.732248 / 0.386340 either way |
| duelist mirror, 600 frames | at 60, 200, 400, each stepped 1 s | a second instance: exact, teleport into a fresh one, teleport into a shared one | bit-identical, all three |

A seed-swapped control in the fought-bout test shows that the history hash can tell two bouts apart.

**A bout does not depend on what its instance built before it**, in the two cases tried: a duelist
mirror and a brawler-miser bout, 900 frames each. Building and discarding one or three scratch bouts
first, or building the bout while another is alive in a second instance, changed nothing to the bit.

The warning in the header of `src/golem/duel-model.ts` (allocator and solver history can flip a
winner) was not reproduced here. It is not what makes an exact fork need a fresh instance. The reason
is in section 3.

## 3. Two kinds of fork

**Teleport.** The capture is written into a world built by the same code, through Havok's getters
and setters. What no getter reaches is the solver's memory: contact manifolds, warm-start impulses
and the broadphase. Those start cold in the fork.

The teleport-floor test (brawler v miser, frame 240, Node bout runner) puts a fork 7.465 mm from its
original after one frame. The control is a world built the same way from other seeds and never
restored; it is more than 100 mm away. After that the gap grows, as section 4 shows.

**Exact.** Havok is one wasm instance, and all its state is that instance's linear memory.
`captureBout(bout, { heap: true })` slices the memory, and `exactFork` does three things:

1. builds the same bout into a fresh instance;
2. copies the slice over that instance;
3. writes the JavaScript graph.

The fork is then the original. It needs two conditions, and `copyHeap` checks both:

- **It needs an instance of its own.** The copy would otherwise overwrite the original.
- **Every body has the address the original's has.** JavaScript holds each body and joint by its
  address in the heap. Two worlds built by the same code into fresh instances get the same
  addresses. A bout built into an instance that had held one scratch bout got none of its 67 body
  addresses the same (Node bout runner, duelist mirror), although it then fought identically. That
  is why the original itself must also be built into a fresh instance.

**Joints made mid-bout get their own address.** A maul's second hand closing on the haft is a joint
made mid-bout. The fork replays it at a moment of its own, so it gets another address. Joints are
therefore paired by key rather than by address. Once the original's memory is in, the fork's joint
is pointed at the original's, which is in the copy. Without that step, a maul build crashes inside
Havok ("null function or function signature mismatch").

**What was checked** (Node bout runner, a second fresh instance per fork):

- The fork is compared with its original every frame for 300 frames, after 300 frames of bout, with
  and without a sever.
- It is bit-identical, and so is the bout's full result, for:
  - the shipped golems;
  - two mauls against a fist;
  - a human with two mauls against a skeleton with fist and whip;
  - the odd build.

`an_exact_fork_is_its_original_to_the_bit_even_after_a_sever` holds the first two, with a teleport
fork beside them as the control. Each of three mutations turns it red:

- skipping the heap copy;
- skipping the joint remap;
- going back to a walk that reads only enumerable fields.

That last mutation is how the exact fork found missing state the graph comparison could not: the
recorder's engagement tracker is non-enumerable. A teleport fork had been forking every bout with
that tracker at its build state, which showed as an engagement count off by one.

## 4. Divergence against horizon

Fork study, 70 mirror bouts of the five probe minds (seeds 0 to 13 of each), forked at 222 moments.

- **Moments.** The first moment is at 0.8 s plus up to 0.5 s of jitter, past the seed-independent
  opening. Later moments are 4.6 s apart, each with its own jitter, until the bout ends.
- **Per mind:** brawler 53, champion 46, duelist 53, miser 32, needle 38. The miser's bouts end
  soonest.
- **Readings.** Distances are between the fork and the original, in mm. "Root" is the locomotion
  module's root part. "Tip" is the primary effector's tip, while it is attached. The n is two sides
  times the moments whose bout was still running at that horizon.
- **Four worlds are stepped beside the original from each moment:**
  - **teleport, open loop:** driven by the commands the original applied, substep by substep, so
    what diverges is the physics alone;
  - **teleport, closed loop:** driven by its own restored minds, which is what a rollout is;
  - **exact:** closed loop;
  - **exact, the opponent's dice restarted:** the right side's mind reseeded at the moment.

**Teleport, open loop**

| horizon | n | root median | root p90 | tip median | tip p90 |
|---:|---:|---:|---:|---:|---:|
| 0.1 s | 444 | 0.0 | 0.0 | 9.5 | 58.6 |
| 0.25 s | 442 | 0.0 | 0.1 | 13.9 | 126.5 |
| 0.5 s | 436 | 0.0 | 2.0 | 16.8 | 158.8 |
| 1 s | 428 | 0.0 | 8.6 | 31.5 | 363.2 |
| 2 s | 400 | 0.0 | 23.7 | 22.0 | 639.2 |
| 4 s | 366 | 0.0 | 934.1 | 42.9 | 1636.1 |

**Teleport, closed loop**

| horizon | n | root median | root p90 | tip median | tip p90 |
|---:|---:|---:|---:|---:|---:|
| 0.1 s | 444 | 0.1 | 0.9 | 9.7 | 60.1 |
| 0.25 s | 442 | 0.3 | 5.7 | 14.1 | 167.9 |
| 0.5 s | 436 | 1.3 | 25.5 | 27.7 | 280.1 |
| 1 s | 428 | 5.1 | 88.3 | 67.9 | 669.6 |
| 2 s | 400 | 17.4 | 254.3 | 90.3 | 1083.6 |
| 4 s | 366 | 61.5 | 1061.8 | 222.1 | 1870.2 |

**Exact**: 0.0 at every horizon, root and tip, median and p90. That is 444 to 366 readings each, and
every one is exactly zero.

**Exact, the opponent's dice restarted**

| horizon | n | root median | root p90 | tip median | tip p90 |
|---:|---:|---:|---:|---:|---:|
| 0.1 to 1 s | 444 to 428 | 0.0 | 0.0 | 0.0 | 0.0 |
| 2 s | 400 | 0.0 | 17.4 | 0.0 | 5.3 |
| 4 s | 366 | 187.9 | 1611.1 | 204.2 | 1316.7 |

**Reading the tables.**

- **The root is a poor measure of physical divergence** under open loop. A golem's root follows its
  carrier, whose state is JavaScript driven by the command. It moves only when a contact pushes the
  stability ledger, which is the p90 column.
- **The tip is the honest measure.** Under open loop it settles back towards the commanded pose
  between strokes, which is why its median falls from 1 s to 2 s.
- **Closed loop compounds.** Each mind reads a slightly different world and decides slightly
  differently. By 1 s the median tip is 68 mm off and one in ten is 0.67 m off.
- **The exact fork does not diverge at all**, so everything a teleport fork gets wrong comes from the
  cold solver and the teleport. Nothing is missing from the capture.
- **The opponent's dice do not show before 2 s.** The probe minds draw rarely: in the mind test, a
  reseeded duelist first decides differently 279 decisions (2.3 s) after its snapshot.

## 5. Ranking fidelity

Fork study, the same 222 moments. Four command prefixes are held on the left side for 0.5 s, and then
the left side's mind runs on:

- `own`: the mind unchanged;
- `press`: forward, acting hand thrusting;
- `withdraw`: back, acting hand guarding;
- `circle`: strafe.

Each prefix is run in four worlds. The first is the reference, a replay of the bout from t = 0 in a
fresh instance, checked bit-identical in pose and damage with the original at the moment. The other
three are ranked against it: a teleport fork, an exact fork, and an exact fork with the opponent's
dice restarted. That restart uses one reseed for all four prefixes, so the prefixes are compared on
common random numbers, as a planner would.

The score is damage dealt minus damage taken by the left side over the horizon, in the runner's
damage units. At 1 s the reference's best and worst prefixes differ by a median of 0.81 (p10 0.10,
p90 2.27).

**The columns.**

- **all tied:** the reference scored all four prefixes the same.
- **identical:** the fork's four scores equal the reference's to the bit.
- **pairwise:** the share of the reference's untied pairs that the fork orders the same way. A tie in
  the fork counts half. Chance is 0.5.
- **top-1:** among moments with a unique best prefix, the share where the fork's unique best is the
  same one. Chance is 0.25.
- **order:** the whole order agrees.
- Intervals are 95 % bootstrap over bouts, each bout resampled with all its moments, since moments
  in one bout are not independent.

| fork | horizon | all tied | identical | pairwise [95 %] | top-1 [95 %] (n) | order [95 %] |
|---|---:|---:|---:|---|---|---|
| teleport | 0.5 s | 55 | 43 | 0.819 [0.779, 0.858] | 0.721 [0.629, 0.807] (136) | 0.527 [0.451, 0.605] |
| teleport | 1 s | 14 | 6 | 0.743 [0.703, 0.782] | 0.582 [0.510, 0.651] (182) | 0.346 [0.278, 0.411] |
| teleport | 2 s | 10 | 3 | 0.685 [0.648, 0.724] | 0.503 [0.437, 0.569] (193) | 0.217 [0.161, 0.279] |
| exact | 0.5, 1, 2 s | 55, 14, 10 | 222 of 222 | 1.000 | 1.000 | 1.000 |
| exact, dice | 0.5 s | 55 | 221 | 1.000 [1.000, 1.000] | 1.000 [1.000, 1.000] (136) | 1.000 |
| exact, dice | 1 s | 14 | 221 | 1.000 [1.000, 1.000] | 1.000 [1.000, 1.000] (182) | 1.000 |
| exact, dice | 2 s | 10 | 201 | 0.991 [0.984, 0.997] | 0.984 [0.967, 1.000] (193) | 0.962 [0.935, 0.986] |

**Teleport pairwise agreement by mind** (fork study):

| mind | 0.5 s | 1 s | 2 s |
|---|---:|---:|---:|
| golem-duelist | 0.879 | 0.806 | 0.767 |
| golem-miser | 0.863 | 0.797 | 0.722 |
| golem-champion | 0.823 | 0.769 | 0.685 |
| golem-researched-needle-v1 | 0.769 | 0.650 | 0.619 |
| golem-brawler | 0.686 | 0.644 | 0.603 |

The closer and more contact-heavy the fight, the faster a cold start scrambles the ranking. The
brawler is worst.

### The gate threshold, from the data

The expert (session 04) will plan with the opponent's real mind reseeded: it knows the policy and
not the dice. So the least a planning fork must do is rank no worse than the dice themselves already
scramble the ranking. Over twice the planning horizon (2 s) the dice kind's lower bounds are 0.984
pairwise and 0.967 top-1. Rounded down, **the threshold at 1 s is pairwise agreement ≥ 0.98 and
top-1 ≥ 0.95**, on the probe-mind mirrors in the fork study.

- **The exact fork passes**, at 1.000 and 1.000.
- **The teleport fork fails**, at 0.743 and 0.582.
- **The chance rule does not trigger for either.** At 0.5 s the teleport fork's lower bounds (0.779
  pairwise, 0.629 top-1) are far above chance (0.5 and 0.25).

## 6. Cost

**One lane** (`.review/fork/cost0.mjs`, not committed; Node bout runner). Three pairings (duelist
mirror, brawler v miser, champion mirror), six moments each, a second apart, 18 samples. The host was
busy (88 % CPU load from other work), so these are an upper bound on a quiet host.

| step | median ms | p90 ms |
|---|---:|---:|
| capture (graph and native) | 20.0 | 28.3 |
| capture with the heap (16.9 MB) | 26.2 | 35.2 |
| a fresh Havok instance | 18.2 | 53.2 |
| teleport fork: build | 39.9 | 85.1 |
| teleport fork: restore | 29.2 | 47.2 |
| exact fork, all of it (fresh instance, build, heap copy, restore) | 92.9 | 145.8 |
| exact fork: build | 41.5 | 82.9 |
| exact fork: restore, heap copy included | 32.5 | 45.9 |
| one simulated second of a fork | 222.4 | 326.1 |
| one simulated second of the original, for comparison | 242.8 | 328.0 |

**Six lanes** (fork study, the 222 moments, with other worlds alive in each lane):

| step | median | p90 |
|---|---:|---:|
| capture | 32.9 ms | 48.0 ms |
| capture with the heap | 40.8 ms | 64.6 ms |
| exact fork | 144.0 ms | 250.2 ms |
| one simulated second | 350.6 ms | 619.9 ms |

The graph holds a median of 3351 nodes (p90 4415).

**Memory.** An exact fork's instance is collected when the fork is disposed. Sixty exact forks in a
row held the process at 345 to 438 MB RSS with no growth (Node bout runner).

**What it means for a budget.** A rollout second costs what a bout second costs, and an exact fork
adds about 93 ms to each rollout, some 40 % of a simulated second. One decision over 32 one-second
rollouts is then
about 32 × (93 + 222) ms ≈ 10 s on one busy lane. That is about 1/80 of real time at 8 decisions a
second.

## 7. For sessions 03 and 04

- **Plan on exact forks.** Build the bout being planned into a fresh instance (`freshHavok()`); the
  exact fork refuses otherwise. Capture once per decision with `{ heap: true }`, then call
  `exactFork` once per candidate.
- **A start state for a drill (session 03)** can be an exact capture of a real bout at a chosen
  moment. It is data: a heap slice and a graph, 17 MB and a few thousand nodes.
- **Full knowledge is `restoreMind(mind, snapshotMind(mind), { reseed })`** on the fork's opponent
  (`world.right.mind`). Over one second it almost never changes an outcome against these minds. A
  full-knowledge expert will therefore mostly be planning against the opponent's actual future,
  which the model-only instrument cannot, and the gap between the two instruments should be read
  with that in mind.
- **A bout is chaotic at a second.** A 7 mm cold start flips a quarter of prefix pairs by 1 s. Any
  predictor that is not exact (session 04's model-only instrument, a learned model) inherits at least
  that much ranking noise, and more against a brawler.
- **Handles.**
  - Only joints may get new addresses; they are remapped by key.
  - A body made mid-bout would break the address match, and `copyHeap` throws rather than fork
    wrongly. Nothing makes one today.
  - The remap touches `_constraintToBodyIdPair`, which the rebuild-lifecycle audit wraps.
- **Minds outside the audit** (section 1) must be run through `auditClosures` before a fork of them
  is trusted.
- **Two cheapenings not taken.**
  - A pool of built fork worlds reused across candidates would save the build (about 40 ms). A heap
    copy resets Havok, but not the JavaScript topology after a rollout that severed something.
  - Deciding with fewer, longer rollouts trades the same budget the other way.
