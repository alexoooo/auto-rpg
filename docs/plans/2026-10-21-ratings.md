# Ratings: one way to evaluate, a history that keeps every result

## Direction

Every question of how well something does (a mind in the field, a skill at its task, a choice
at a moment) is asked the same way. An **evaluation** names its conditions, builds a case's world
for the subjects it is given, reads the case in its task's units, and the runner combines the
readings. One definition serves the Node runner, the gate's tests and a new top-level **Ratings**
screen (`?play=ratings`), which browses results and their history, opens any case to watch it,
and runs evaluations live in the browser.

**Nothing measured is thrown away.** Every run is kept as a record of games, with what played
them. Everything rated has the coordinates `{ id, version }`: a stable id, and a version computed
from what the thing is. A change gives a new version with its parent recorded.

**Results are compared where they are comparable.** A **pool** is an evaluation's games under one
play protocol and one environment: the code that builds and plays a case, apart from the
subjects' own. Within a pool, everything plays under the same rules and physics, and one rating
per `{ id, version }` is fitted. Older pools stay visible as history, marked with what changed
between them. Carrying a strength across a changed environment is a model to be validated, not
an assumption (step 13).

**The everyday report is a paired one.** A change to a mind or a skill is read against its
previous version, on the same conditions, against a fixed, varied panel, in the units of its
task: score per matchup for a contest, a figure for a battery. Difficult matchups and coverage
are shown beside the total. The whole league runs at checkpoints, sparsely, and Elo summarises it.

Speed comes from what is asked, not from shortcuts in the cache:
- A change is read against its previous version and the panel, within a budget, and stopped once
  the answer is clear. An inconclusive answer within the budget is a result.
- The league runs on a sparse schedule, at checkpoints.
- A case is never played twice at the code it depends on, and a change replays only the cases
  whose code it touched.

### What the 10-hour tournament says

The tournament written at `d06fb568` (`assets/minds/ratings.json`) was played on the source of
`1bacac44`: 107 entrants, 11,342 bouts, Node, core world, rapier-coordinate, 120 Hz, protocol
`76b07355f926f9df`. Its 107 ratings, fitted by least squares:

| Model of an entrant's rating | R² | rms left, Elo | Parameters (identified) |
|---|---|---|---|
| mind | 0.13 | 207 | 10 |
| loadout | 0.47 | 161 | 5 |
| mind + character + loadout | 0.61 | 139 | 17 |
| mind + character + left item + right item | 0.61 | 139 | 16 |
| mind + character + loadout + mind x loadout | 0.81 | 96 in sample, about 120 corrected | 39 |

- **The kit matters more than the mind.** A mind's standing has to be read with kits held alike.
- **The item in each hand explains as much as the loadout.** The representative set barely tests
  this: the left hand is only empty or buckler, and five loadouts cover five of the six
  combinations.
- **A mind uses kits in its own way.** What is left after shared factors is above an entrant's
  own uncertainty: the median 95 % interval is 124 Elo wide, about 32 Elo of standard error. So
  the ratings stay per entrant. Shared factors are a candidate for sparse play (step 11), kept
  only if they predict held-out games better.

These figures are a fit to the ratings, not to the games. They are read again from the games
once the rows are imported (step 5).

`ratings.json` holds no endings or lengths, so how many bouts ran to the 120 s cap is unknown.
At the cap the bars decide the winner (`Duel`, `src/arena/duel.ts`), so the 3 % draw rate does
not answer it. The rows answer it in step 5.

## The format

### Evaluations

`src/evaluation/` is browser-safe (no `node:` import, no DOM, no `process`), so Node, workers and
the screen run one code path. Everything in it computes with `src/core/math/real.ts` (its `exp`,
and the log it gains), so a world, a verdict and a table come out the same in Node and in a
browser. A module that builds a case's world joins `WORLD_BUILDERS`
(`tests/core-boundary.test.mjs`). Each case kind says whether it is held to bit equality between
engines (`exact`); bouts are, falls are not yet (step 12).

An evaluation is two modules, so that what plays a case and what describes and combines its
readings change apart:
- its **case module** (`src/evaluation/<id>/cases.ts`): conditions, how a case's world is built,
  and how it is read;
- its **description** (`src/evaluation/<id>/index.ts`): title, question, figures, analysis
  settings and default subjects. It imports the case module; nothing a case plays imports it.

```ts
// src/evaluation/evaluation.ts

/** Plain finite JSON: what survives a key, a record, a URL and postMessage. */
export type Json = null | boolean | number | string | readonly Json[] | { readonly [key: string]: Json };

/** Who or what is ranked. A mind or chooser is named by data and resolved through its catalogue. */
export interface Subject {
  /** Stable and readable: what the history follows. */
  readonly id: string;
  readonly label: string;
  /** What it is made of, by id: ["mind:duellist", "model:workshop-rogue", "left:buckler", "right:sword"]. */
  readonly parts: readonly string[];
  readonly value: Json;
}

/** What one case is played in. One builder each (`playCase`), switched with a `never` default. */
export type CaseWorld =
  | { readonly kind: "bout"; readonly engine: string; readonly recipe: DuelRecipe; readonly tape: readonly OrdersEntry[] }
  | { readonly kind: "point"; readonly engine: string; readonly recipe: DuelRecipe; readonly tape: readonly OrdersEntry[];
      readonly step: number; readonly horizon: number }
  | { readonly kind: "fall"; readonly engine: string; readonly fall: FallCase };

/** A reader follows a built case and says when it has what it needs. */
export interface Reader<R extends Json> {
  afterStep(): void;
  readonly ended: boolean;
  reading(): R;
}

/** The case module: everything a case's play depends on, and nothing else. */
export interface Cases<C extends Json, R extends Json> {
  /** How many subjects a case plays: 0 (decision points), 1 (a battery), 2 (a contest, the first on the left). */
  readonly arity: 0 | 1 | 2;
  /** The protocol: what is played and read. Frozen plain data in every case's key. */
  readonly play: Json;
  readonly conditions: readonly C[];
  world(values: readonly Json[], condition: C, engine: string): CaseWorld;
  read(built: BuiltCase): Reader<R>;
}

/** A named figure of the readings, in the task's unit; null where a case does not bear on it. */
export interface Figure<R> {
  readonly name: string;
  readonly unit: string;
  readonly kind: "rate" | "mean" | "median";
  readonly better: "higher" | "lower";
  of(reading: R): number | boolean | null;
}

/** The description: read only by the runner's analysis, the CLI and the screen. */
export interface Evaluation<C extends Json, R extends Json> {
  readonly id: string;
  readonly title: string;
  readonly group: "fighters" | "skills" | "decisions";
  /** One sentence the screen shows above the table. */
  readonly question: string;
  readonly cases: Cases<C, R>;
  /** How readings are combined: figures' settings, the default panel, renamed ids. In no key. */
  readonly analysis: Json;
  /** The default subjects, or those chosen; a mind's JSON config gives one subject per character and loadout it fits. */
  subjects(choice: SubjectChoice): readonly Subject[];
  /** A contest's reading carries `score` (0, 0.5, 1 for the left). */
  readonly figures: readonly Figure<R>[];
}
```

`EVALUATIONS` (`src/evaluation/evaluations.ts`) is the one catalogue the CLI, the tests and the
screen read. An evaluation reads every record of its own: if it changes the shape of its reading,
its figures keep reading the old shape, or it takes a new id.

### Case identity

A case's row is reused when nothing it plays has changed. The line between what a case plays and
what it does not is the one the project already draws between the toolkit and an entrant:
- **Kept:** editing a description, an analysis setting, a screen, a script, a research file, one
  entrant (for every case without it), or the list of entrants and evaluations.
- **Invalidated:**
  - editing the toolkit's play code or data: a new environment and a new pool;
  - editing an entrant: its own cases.

**The environment** is a SHA-256 over:
- the static import closure, including imported JSON, of `src/evaluation/play.ts` and the
  evaluation's case module, cut at the cut points below;
- the lockfile, the vendored solver and the installed Rapier files, as `currentBuildIdentity`
  reads them now.

Files are hashed as `hashBuildInputs` hashes them, with line endings normalised.

Today that closure is about 250 files. Through `src/core/mind/catalog.ts` and
`src/core/models.ts` (whose humanoid default is the `OPTIONS` preset), it holds the built-in minds
(fighter, options, quadruped), every skill, and every preset in `src/core/mind/config.ts`. So
editing a built-in mind or a built-in preset is a toolkit change: a new environment. That is
conservative and correct, and is what `AGENTS.md` already calls it.

**The cut points** are files whose bytes are no case's play:
- **The kinds list** (`src/core/mind/kinds.ts`): imports and one array of kind entries, nothing
  else. It is split out of `src/core/mind/controllers.ts`, whose logic (`registry`,
  `controllerOf`, the fit and fault checks) stays where it is and reads the list.
- **The build identity** (`src/build-identity.ts`, which the bout's recording stamps). Its value
  is the whole tree's, so a reading never holds it: a row holds no recording, save or tape
  identity, only what the case played.

**A case's code** is the environment and, for each mind kind the case's world names, the closure
of that kind's entry less the environment:
- for an entrant, its folder and `assets/entrants/<kind>/`;
- for a built-in kind, its entry module (its controller, slots and fields), since the rest of its
  closure is in the environment already.

A case's world carries every mind's config in full, so a config is data in the key, not code: a
built-in preset's earlier value can be played again at the current code as a JSON mind.

**The key** is the digest of `{ evaluation, play, engine, world, seconds, code }`. The world holds
the subjects' values in full, so the key holds no index or label: adding a subject or renaming a
field changes no other case's key.

The code is computed by `caseCode` (`scripts/build-identity.mjs`). The browser's twin reads the
same from a file table of hashes and import edges, which the Vite plugin
`recording-build-identity` emits. `risingImplementation` (`research/rising-provenance.mjs`)
already walks a closure; the walk moves into `scripts/build-identity.mjs`, and
`risingImplementation` is built on it.

`tests/evaluation-closure.test.mjs`:
- parses the kinds list with TypeScript's parser and refuses anything but imports and the array;
- refuses a non-literal dynamic import in any closure, so the walk is sound;
- edits, in a scratch copy, each of the following, and checks the effect on the keys of a fixed
  set of cases:

  | Edit | Keys changed |
  |---|---|
  | a description | none |
  | `src/arena/main.ts` | none |
  | `scripts/build-identity.mjs` | none |
  | a line of the kinds list | none |
  | one entrant's file | that entrant's cases only |
  | `src/core/mind/fighter.ts` | every case |

### Cases, schedules and comparisons

The runner, not the evaluation, makes the cases. A case is `{ subjects, condition, world,
seconds }`.
- **Arity 0:** each condition. **Arity 1:** each subject on each condition.
- **Arity 2**, by schedule, each pair on both sides and every condition:
  - `all`: every pair.
  - `versus { panel }`: every subject against every panel member.
  - `sparse { opponents, seed }`: each subject meets the `opponents` others with the lowest draw
    of the digest of the sorted pair and the seed. The schedule is the union, so a subject meets
    between `opponents` and about twice as many.
- **The unit of evidence** is a pair: one condition played with each side on the left. A pair is
  sampled whole, and its two cases are never split between a verdict and a gap.
- **Case order** is a seeded shuffle of pairs, so a prefix is a fair sample. A verdict or table
  reads only the longest prefix complete in that order, so it depends neither on the number of
  lanes nor on which case finished first.

A **comparison** names its question and its baseline, and answers in the task's units:
- `head-to-head A B`: does A beat B? The mean of A's pair scores against B, less one half.
- `panel A' A`: does A' do better than A against the panel? The mean over the panel's pairs of A'
  less A on the same member and condition. A's rows may come from a record in the same pool, so
  A's code need not run again.
- `battery A' A`: is A' better at the task than A? Each figure's paired difference over the
  conditions both played.

These are different questions: a new version can beat its parent and do worse against the panel.
The report gives each one asked, and also:
- the per-member and per-condition differences;
- the worst matchups;
- the conditions only one side played.

**Stopping.** `--until settled` runs a sequential test on a comparison's mean, with bounds in its
own units (for a contest, score per pair, e.g. 0 and 0.05), error rates `alpha` and `beta`, and a
budget of pairs. Its variance is regularised by one pair at each extreme, and it needs a minimum
number of pairs before it can settle, so a run of early wins cannot. It ends:
- **better**, **not better**, or **inconclusive** at the budget;
- **incomplete** if a pair is missing for a fault that can be retried.

An interval says what it covers: pairs of the named conditions and panel, at their code.

### Faults

A row is `{ key, reading, digest, fault }`.
- **The case's own faults are results**, recorded and reused:
  - an error thrown inside the case is a `fault`;
  - a non-finite state is an `invalid` fault.
- **The machine's faults can be retried:**
  - a worker's death;
  - the wall-clock watchdog (`--case-minutes`, default 30).

  Each is reported, and leaves the row missing.
- **A missing row stops the analysis**: no verdict, table or record forms past it. A comparison
  with a fault row in its prefix says so beside its answer.

### Records

Working rows are `research/runs/evaluations/<id>/<shard>.jsonl`, read from every file in the
folder, so shards from two machines merge by copying files. Rows are found by key.
- **Two rows with one key must agree:** same reading, same digest, same fault. If they do not, the
  run stops and names both. It is nondeterminism or a defect, never a choice.

`npm run evaluate -- <id> --write` writes a **record** from the merged rows:
`assets/evaluations/<id>/<yyyy-mm-dd>-<commit8>-<keys8>.jsonl`, where `keys8` is the digest of its
case keys.
- **Writing is refused when:**
  - a file in any of its cases' code differs from its commit, or is not tracked;
  - a file of that name exists with other content;
  - a row is missing.
- **Records are never rewritten.** They hold games, not conclusions: every table and rating is
  derived when read, and names the analysis settings it was derived with, so changing the analysis
  rewrites nothing.
- **Reading across records holds the same rule:** a key in two records with differing readings is
  refused, naming both.

**The header line:**
- the identity (`recordingIdentity(BUILD_IDENTITY, "evaluation/1", { engine, harness, play })`),
  commit, date, harness and schedule;
- the pool: the play protocol's digest and the environment's digest;
- each subject in full: its id, label, parts and value, and for it and each of its parts, the
  version and the parent (below).

**Then one line per case:** `{ subjects, condition, key, code, world, reading, digest, fault }`.
The world is stored, so any recorded case can be opened without its definition.

### Versions, ancestry and pools

**Everything rated has the coordinates `{ id, version }`**: a subject, and each of its parts (a
mind, a character, an item in a hand).

- **The id is stable and readable.** For example `duellist/workshop-rogue/buckler,sword` for an
  entrant, `mind:duellist`, `model:workshop-rogue`, `right:sword`. It is what a person names and
  what history follows. A JSON mind is its own id until it is adopted as a preset. A renamed id
  is mapped in `analysis.renames`.
- **The version identifies content, nothing else.** It is the digest of:
  - its **own content**:
    - a mind's config, and its kind's code: the closure of its kind entry less the environment
      (for an entrant, its folder and `assets/entrants/<kind>/`);
    - a character's `BodySpec`, as its model builds it;
    - an item's `ItemSpec` (`heldItem`, `src/core/items/held.ts`);
    - for an entrant, its parts' together;
  - its **pool**: the play protocol and the environment.

  Nobody bumps a version, and nobody can forget to.
- **The record states the parent.** When a version first appears in a record, the record writes
  its parent:
  - the baseline the run named with `--previous`;
  - otherwise, the version of the same id in the newest record on the current branch's
    first-parent history (`git log --first-parent` over `assets/evaluations/<id>/`).

  First-parent history is one order, and it is local: a record in the tree came with the commit
  that added it. Dates never decide ancestry.
- **Parents form a graph, not a tree.** Returning to earlier content is that earlier version, and
  two branches can make the same content from different parents. The screen shows each recorded
  edge, orders a series by first appearance in first-parent history, and refuses nothing.
- **Changes from the parent** are each part of the version that differs. The digests are stored
  apart, so the screen can say which:
  - `own`: the config, or the kind's code;
  - `protocol`: the play protocol;
  - `environment`: the toolkit, including the built-in minds and skills.
- **Readable labels.** The screen shows a version by its order in the id's history and the
  record it first appears in: `duellist v3 (2026-10-24, 5f1c09ab)`. The digest is the key; `v3`
  is only its label.
- **Identity, ancestry and baseline are three things.**
  - The digest says what a thing is.
  - The parent says what it was developed from.
  - A comparison names the baseline it tests against, which is often the parent but need not be.

A **pool** is an evaluation's games that share a play protocol and an environment. Versions in
one pool are compared directly. A skill's code is part of the environment until skills live in
folders of their own, as the workshop plan's component folders propose; a folder is then cut out
of the environment and enters a case's code by the same rule as a mind's kind.

### Ratings within a pool

`src/evaluation/rating.ts` takes `bradleyTerry` and `ratingIntervals` from `research/rating.mjs`
onto `real.ts`. One strength per `{ id, version }` of the pool's subjects, fitted over the pool's
distinct case keys. `P(i beats j) = 1 / (1 + 10^((s_j - s_i) / 400))`, a draw half a win, with
the existing half-game prior and pair bootstrap.

What the screen shows:
- **For an entrant:** its rating with an interval, its score against each opponent, and its
  worst matchups.
- **For a mind, a character or an item:** a comparison on common ground. Two minds are compared
  on the characters and loadouts both fit, by their entrants' paired results there. Coverage (the
  kits one fits and the other does not) is shown beside the comparison, never averaged into it. A
  mind is not ranked by its average over the kits it fits, which would reward a narrower, easier
  set.

**History across pools** is shown, not fitted. A subject's progression is a series:
- its standing in each pool (rank and rating against that pool's field);
- the panel comparison of each version against its parent, where one was played;
- the changes between the pools.

Batteries (arity 1) need no rating model. A version's figures are its own. Its change from its
parent is the paired difference over the conditions they share, with an interval. Its
progression is the series of its figures.

### 13. Strength across pools, if it predicts

A model carrying strength from one pool to the next is built only if it is measured to help:
- each version tied to its parent by a prior whose width depends on the kind of change, as
  Whole-History Rating ties it over time;
- fitted jointly, with intervals from the full inverse Hessian.

The test is predictive: fitted on pools up to one, does it predict the next pool's games better
than that pool's own fit at the same number of games, and do its intervals cover at their stated
rate? Until it passes, the screen shows history across pools as a series (above), and the model
is not shown.

### 14. Decisions

This is separate from the rest: it waits on the owner's decisions below and on an interface to
the AI.
- `decisions` is arity 0. Its conditions are points: a bout recipe and tape at every 0.5 s of its
  play, as the oracle samples them (`research/oracle.mjs`).
- **A point's case** plays to the step, saves (`Duel.save`), and plays each response in a load of
  that save for the horizon. It reads each response's raw outcome: each side's bar, who is out,
  wound dealt and taken, and falls. Wound and falls are new readings.
- The responses move from `responsesAt` (`research/rollouts.mjs`) into `src/evaluation/`, on
  `real.ts`.
- **Values** are computed from the raw outcomes when a table is made, so changing the value
  changes no case.
- **Choosers** are scored in analysis over the points' rows: a chooser's regret at a point is
  the best response's value less its choice's. The reference choosers are `own` (always the
  tactics' own) and the clairvoyant best (zero regret, the ceiling).
- **Your decisions, before choosers below the tactics can be read:**
  1. *The common value unit.* Proposed: the oracle's `valueOf`, own bar less the foe's and a
     point either way for an out, over a 2 s horizon.
  2. *How a chooser is asked.* Ranking responses from one side's senses needs an interface
     between the mind and the evaluation. Ranking skills, not orders, also needs an order that
     asks for one action and a fork that honours it. Both change the AI's structure.
