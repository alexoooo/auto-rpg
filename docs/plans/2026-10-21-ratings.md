# Ratings: one way to evaluate, a history that keeps every result

## Direction

Every question of how well something does (a mind in the field, a skill at its task, a choice
at a moment) is asked the same way. An **evaluation** names its conditions, builds a case's world
for the subjects it is given, reads the case in its task's units, and the runner combines the
readings. One definition serves the Node runner, the gate's tests and a new top-level **Ratings**
screen (`?play=ratings`), which browses results, shows how each subject has progressed, opens any
case to watch it, and runs evaluations live in the browser.

**Nothing measured is thrown away.** Every run is kept as a record of games. Everything rated
has the coordinates `{ id, version }`: a stable id, and a version computed from what the thing
is. When its configuration, its own code, the shared code or the protocol changes, it has a new
version linked to its parent. Ratings are one fit over every game in every record. A version's
strength is tied to its parent's by a prior whose width depends on what changed, so a change
never discards what was known. A new version is compared with its previous one directly, and
every subject's progression is visible.

Speed comes from what an evaluation asks, not from shortcuts in its cache:
- A candidate is read against its previous version and a fixed panel, and stopped once the result
  is settled.
- A field is read on a sparse schedule whose ratings borrow strength from shared factors (mind,
  character, the item in each hand) and from the subjects' history.
- A case played once at its code is never played again.

### What the 10-hour tournament says

The tournament written at `d06fb568` (`assets/minds/ratings.json`) was played on the source of
`1bacac44`: 107 entrants, 11,342 bouts, Node, core world, rapier-coordinate, 120 Hz, protocol

| Model of an entrant's rating | R² | rms left, Elo | Parameters (identified) |
|---|---|---|---|
| mind | 0.13 | 207 | 10 |
| loadout | 0.47 | 161 | 5 |
| mind + character + loadout | 0.61 | 139 | 17 |
| mind + character + left item + right item | 0.61 | 139 | 16 |
| mind + character + loadout + mind x loadout | 0.81 | 96 in sample, about 120 corrected | 39 |

- **The kit matters more than the mind.** A mind's standing has to be read with kits held alike.
- **The item in each hand explains as much as the loadout.** The representative set barely tests
  this: the left hand is only empty or buckler, and five loadouts cover five of the six
  combinations.
- **A mind uses kits in its own way.** What is left after shared factors is above an entrant's
  own uncertainty: the median 95 % interval is 124 Elo wide, about 32 Elo of standard error. So
  factors cannot replace an entrant's rating. They are its prior, and sparse play leans on them
  where an entrant has few games.

At the cap the bars decide the winner (`Duel`, `src/arena/duel.ts`), so the 3 % draw rate does
not answer it. The rows answer it in step 4.

**The run's rows are required to keep it whole.** The machine that ran it holds them at
`research/runs/tournament/<build>-<protocol>.jsonl`, with the unseen report's 384 bouts in the

## The format

### Evaluations

`src/evaluation/` is browser-safe (no `node:` import, no DOM, no `process`), so Node, workers and
the screen run one code path. Everything in it computes with `src/core/math/real.ts` (its `exp`,
and the log it gains), so a world, a verdict and a table come out the same in Node and in a
browser. A module that builds a case's world joins `WORLD_BUILDERS`
(`tests/core-boundary.test.mjs`). Each case kind says whether it is held to bit equality between
engines (`exact`); bouts are, falls are not yet (step 10).

```ts
// src/evaluation/evaluation.ts

/** Plain finite JSON: what survives a key, a record, a URL and postMessage. */
export type Json = null | boolean | number | string | readonly Json[] | { readonly [key: string]: Json };

/** Who or what is ranked. A mind or chooser is named by data and resolved through its registry. */
export interface Subject {
  /** Stable and readable: what the history follows. */
  readonly id: string;
  readonly label: string;
  /** Shared factors' ids, e.g. ["mind:duellist", "model:workshop-rogue", "left:buckler", "right:sword"]. */
  readonly features: readonly string[];
  readonly value: Json;
}

/** What one case is played in. One builder each (`playCase`), switched with a `never` default. */
export type CaseWorld =
  | { readonly kind: "bout"; readonly engine: string; readonly recipe: DuelRecipe; readonly tape: readonly OrdersEntry[] }
  | { readonly kind: "point"; readonly engine: string; readonly recipe: DuelRecipe; readonly tape: readonly OrdersEntry[];
      readonly step: number; readonly horizon: number }
  | { readonly kind: "fall"; readonly engine: string; readonly fall: FallCase };

/** A reader follows a built case and says when it has what it needs. */
export interface Reader<R extends Json> {
  afterStep(): void;
  readonly ended: boolean;
  reading(): R;
}

/** A named figure of the readings; null where a case does not bear on it. */
export interface Figure<R> {
  readonly name: string;
  readonly unit: string;
  readonly kind: "rate" | "mean" | "median";
  readonly better: "higher" | "lower";
  of(reading: R): number | boolean | null;
}

export interface Evaluation<C extends Json, R extends Json> {
  readonly id: string;
  readonly title: string;
  readonly group: "fighters" | "skills" | "decisions";
  /** One sentence the screen shows above the table. */
  readonly question: string;
  /** How many subjects a case plays: 0 (decision points), 1 (a battery), 2 (a contest, the first on the left). */
  readonly arity: 0 | 1 | 2;
  /** What is played and read. Frozen plain data in every case's key. */
  readonly play: Json;
  /** How readings are combined (figures' settings, priors, drifts, renamed ids). In no key. */
  readonly analysis: Json;
  readonly conditions: readonly C[];
  /** The default subjects, or those chosen; a mind's JSON config gives one subject per character and loadout it fits. */
  subjects(choice: SubjectChoice): readonly Subject[];
  /** Each subject's own content: what makes its version, beside the play identity and protocol. */
  ownContent(subject: Subject): Json;
  world(values: readonly Json[], condition: C, engine: string): CaseWorld;
  read(built: BuiltCase): Reader<R>;
  /** Arity 0 and 1. A contest's reading carries `score` (0, 0.5, 1 for the left), its only rated figure. */
  readonly figures: readonly Figure<R>[];
}
```

`EVALUATIONS` (`src/evaluation/evaluations.ts`) is the one registry the CLI, the tests and the
screen read. An evaluation reads every record of its own: if it changes the shape of its reading,
its figures keep reading the old shape, or it takes a new id.

### Cases, schedules and stopping

The runner, not the evaluation, makes the cases. A case is `{ subjects, condition, world,
seconds }`.
- **Its key** is the digest of `{ evaluation, play, engine, world, seconds, own }`, where `own` is
  the digest of its subjects' own content. The world holds the subjects' values in full, so the key
  never holds an index or a label: adding a subject or renaming a field changes no other case's
  key.
- **Arity 0:** each condition. **Arity 1:** each subject on each condition.
- **Arity 2**, by schedule, each pair on both sides and every condition:
  - `all`: every pair.
  - `sparse { opponents, seed }`: each subject meets the `opponents` others with the lowest draw
    of the digest of the sorted pair and the seed; the schedule is the union, so a subject meets
    between `opponents` and about twice as many.
  - `versus { panel }`: every subject against every panel member.
- **Case order** is a seeded shuffle, so a prefix is a fair sample. The stopping rule and the table
  read only the longest prefix complete in that order, so neither depends on the number of lanes
  or on which case finished first.

**Stopping** is on a named **contrast** of paired differences:
- `head-to-head A B`: A's score less one half, over A's cases against B.
- `ablation A' A`: A' against each panel member less A against the same member, on the same
  condition and side. A's rows may come from a record, so A's code need not run.
- "A new version against its previous one" is both at once: the head-to-head between them when
  both can run, and the ablation over the panel.

`settled` runs a sequential probability ratio test (normal approximation, Elo bounds `elo0 <
elo1`, error rates `alpha`, `beta`) on the mean difference. It has a minimum number of pairs and
a variance regularised by one pair at each extreme, so a run of early wins cannot settle it.

### Identity, cache and faults

- **Play identity.** `playIdentity()` (`scripts/build-identity.mjs`) is one SHA-256 over what
  cases can run:
  - the transitive static import closure of `src/evaluation/play.ts` and
    `src/evaluation/evaluations.ts`, including imported JSON;
  - the lockfile, the vendored solver and the installed Rapier files, as `currentBuildIdentity`
    reads them now;
  - **excluding** entrant folders (`src/core/entrants/<kind>/`, `assets/entrants/<kind>/`), which
    are each entrant's own content and enter only its own cases' keys. The boundary test already
    keeps an entrant out of the toolkit and the other entrants.

  `tests/evaluation-closure.test.mjs` refuses a non-literal dynamic import in the closure, so the
  walk is sound. The Vite plugin `recording-build-identity` also emits `PLAY_IDENTITY` for the
  browser. Editing a screen, a script, a research file or one entrant changes no other case's
  key. `risingImplementation` (`research/rising-provenance.mjs`) already walks a closure this way;
  the walk moves into `scripts/build-identity.mjs` and `risingImplementation` is built on it.
- **Cache.** A case's row is reused when its key matches at the same play identity, from a record
  or from working rows. Working rows are `research/runs/evaluations/<id>/<play>/<shard>.jsonl`,
  read from every file in the folder, so shards from two machines merge by copying files.
- **Faults.** A row is `{ key, reading, digest, fault }`:
  - An error thrown inside the case is a `fault`, recorded and reused.
  - A non-finite state is an `invalid` fault.
  - A worker's death or the wall-clock watchdog (`--case-minutes`, default 30) is reported and
    leaves the row missing, since it depends on the machine. A stopping verdict or table does
    not form past a missing row.

### Records and versions

`npm run evaluate -- <id> --write` writes a **record** from the merged working rows:
`assets/evaluations/<id>/<yyyy-mm-dd>-<commit8>-<keys8>.jsonl`, where `keys8` is the digest of
its case keys, so two records never share a name. It is refused if any file of the play closure,
or an entrant folder it plays, differs from its commit. Records are never rewritten. They hold
games, not conclusions: every table and rating is derived when read, so changing the analysis
rewrites nothing.

- **The header line:**
  - the identity (`recordingIdentity(BUILD_IDENTITY, "evaluation/1", { play identity, engine,
    harness, play })`), commit, date, harness and schedule;
  - each subject in full, with its id, label, features and value;
  - for each subject and each of its features, the three parts of its version kept apart: the
    own-content digest, the play protocol digest and the play identity.
- **Then one line per case:** `{ subjects, condition, key, world, reading, digest, fault }`. The
  world is stored, so any recorded case can be opened without its definition.

The **history** of an evaluation is its records in the checked-out tree: Git decides what has
been merged.

**Everything rated has the coordinates `{ id, version }`.** That covers a subject, and each of
its features: a mind, a character, an item in a hand.

- **The id is stable and readable.** For example `duellist/workshop-rogue/buckler,sword` for an
  entrant, `mind:duellist`, `model:workshop-rogue`, `right:sword`. It is what a person names and
  what the history follows. A JSON mind is its own id; it becomes the next version of a preset
  only when the preset's code takes its config. A renamed id is mapped in `analysis.renames`.
- **The version is computed, never typed.** It is the digest of three parts:
  - its **own content**:
    - a mind's config, plus its entrant folder's files if its kind is an entrant;
    - a character's `BodySpec`, as its model builds it;
    - an item's `ItemSpec` (`heldItem`, `src/core/items/held.ts`);
    - an entrant's own content is its mind's, character's and items' together;
  - the **play protocol**;
  - the **play identity**.

  Nobody bumps a version, and nobody can forget to.
- **Readable labels.** The screen shows a version by its order in the id's history and the
  record it first appears in: `duellist v3 (2026-10-24, 5f1c09ab)`. The digest is the key; `v3`
  is only its label.
- **Each version has a parent**: the version of the same id in the latest earlier record that
  holds it. Its **changes** from the parent are each part that differs (`own`, `protocol`,
  `shared` for the play identity); none, and it is the same version.

A rating is read at either coordinate: `{ id }` is its latest version's, and `{ id, version }`
is that version's. A skill's code is part of the play identity, so its change is `shared`, until
skills live in folders of their own, as the workshop plan's component folders propose. From then
on, a folder is own content by the same rule as an entrant's, and leaves the play identity.

### Ratings over history

`src/evaluation/rating.ts` replaces `research/rating.mjs`. It makes one joint fit over every
game of an evaluation's records:
- **Strength.** A subject's strength is the sum of its features' weights and its own term
  (`entrant:<id>`), with main effects only (mind, character, left item, right item), each at its
  version. `P(i beats j) = 1 / (1 + 10^((s_j - s_i) / 400))`, a draw half a win.
- **Each game counts once.** Games are distinct case keys across records.
- **One weight per `{ id, version }`.**
  - A first version's prior is normal about zero, with its group's spread.
  - A later version's prior is normal about its parent's weight, with variance the sum of the
    drifts of its changes (`own`, `protocol`, `shared`).
- **The fit.** Newton's method to a fixed iteration count. Intervals come from the full inverse
  Hessian (the Laplace approximation), so the anti-correlation of an entrant's own term with its
  features is kept.
- **The scale.** Fixed by the priors, not by re-centring: an unchanged subject's strength does
  not move because strong newcomers arrived. The screen centres on the current field only for
  display.
- **The model is Whole-History Rating over versions instead of time.** Hundreds of versions is a
  dense matrix of a few megabytes. When the history outgrows that, earlier play identities are
  folded into a Gaussian prior with full covariance, which loses nothing the approximation keeps.

What the screen shows:
- **Marginal predicted strengths, with intervals:** a mind's strength averaged over the kits it
  fits, an item's averaged over the minds that hold it. A raw coefficient is not shown, because
  a mind restricted to some characters is confounded with them.
- **Where the priors come from.** The group spreads and the three drifts are analysis settings,
  set from measurement (steps 4 and 6), with the readings in the commit message.

Batteries (arity 1) need no rating model. A version's figures are its own. Its change from its
parent is the paired difference over the conditions they share, with an interval. Its
progression is the series of its figures.

### 6. Sparse fields and settled comparisons

- `sparse`, the contrasts and `settled` stopping in `schedule.ts`, `stats.ts` and `run.ts`.
- **Reading the sparse default.** Measured against the 10-hour record, with `opponents` 8, 16 and
  32 on five seeds: each schedule's rank correlation with the full run, its largest gap, and its
  bouts. Choose the default `opponents`, and give the table in the commit message.
- **New against previous.** `npm run evaluate -- tournament --mind new.json --previous duellist
  --until settled` reads a new config against the duellist's latest version, head-to-head and over
  the panel.
  - **After an own-only change** (a config, or an entrant's folder), the panel's rows from the
    previous version's record are still valid. The ablation pairs the new rows with the recorded
    ones, and the old version need not run.
  - **After a shared change**, the panel plays again at the new code, and the comparison is the
    fit's difference between the two versions, with its interval. It is labelled as the fit's,
    not a settled test.
  - The drifts are read from the first records that re-measure the same ids, and given in the
    commit message.
- Tests:
  - `tests/evaluation-schedule.test.mjs`: sparse degrees within bounds; deterministic for a
    seed; `versus` pairs exactly the panel.
  - `tests/evaluation-stopping.test.mjs`: on scripted pools, 70 % settles for, 30 % against,
    50 % runs out, four early wins do not settle, and an ablation against recorded rows settles
    as one played live.

### 11. Decisions

- `decisions` is arity 0. Its conditions are points: a bout recipe and tape at every 0.5 s of its
  play, as the oracle samples them (`research/oracle.mjs`).
- **A point's case** plays to the step, saves (`Duel.save`), and plays each response in a load of
  that save for the horizon. It reads each response's raw outcome: each side's bar, who is out,
  wound dealt and taken, and falls. Wound and falls are new readings.
- The responses move from `responsesAt` (`research/rollouts.mjs`) into `src/evaluation/`, on
  `real.ts`.
- **Values** are computed from the raw outcomes when a table is made, so changing the value
  changes no case.
- **Choosers** are scored in analysis over the points' rows: a chooser's regret at a point is
  the best response's value less its choice's. The reference choosers are `own` (always the
  tactics' own) and the clairvoyant best (zero regret, the ceiling).
- **Your decisions, before choosers below the tactics can be read:**
  1. *The common value unit.* Proposed: the oracle's `valueOf`, own bar less the foe's and a
     point either way for an out, over a 2 s horizon.
  2. *How a chooser is asked.* Ranking responses from one side's senses needs an interface
     between the mind and the evaluation. Ranking skills, not orders, also needs an order that
     asks for one action and a fork that honours it. Both change the AI's structure.
