# Ratings: one way to evaluate, a history that keeps every result

## Why

Every question of how well something does (a mind in the field, a skill at its task, a choice at
a moment) is asked one way. An **evaluation** names its conditions, builds a case's world for its
subjects and reads it in its task's units; the runner combines the readings. One definition serves
the Node runner and a top-level **Ratings** screen (`?play=ratings`) that browses results and
history, opens any case to watch, and runs evaluations live.

- **Nothing measured is thrown away**: every run is kept as a record of games, and history is
  compared where comparable (a rating within a pool, a series across pools).
- **The everyday report is paired**: a change against its previous version, on the same
  conditions, against a fixed, varied panel, in its task's units, with difficult matchups and
  coverage beside the total. It replaces the full tournament.
- **Each kind of thing is rated by the experiment that isolates it**: an entrant (body,
  attributes, items, mind) in the league; a mind against another on the kits both fit; an item, a
  character, an attribute one at a time (step 9); a skill on its task and by what removing or
  replacing it does in a fight (step 10).
- **Speed comes from what is asked**, under [AGENTS.md](../../AGENTS.md)'s long-run rule (expected
  wall time first, an iteration in about 10 minutes, nothing over an hour without the owner's
  go-ahead). A report stops within its budget once its answer is clear; inconclusive is a result.
  A bout gives its bar margin as well as its winner, and runs no longer than its verdict needs
  (step 6). No setting is chosen by a run played only to choose it: margin, cap and schedule come
  from the imported 10-hour rows and the rows reports play anyway. No case is played twice at the
  code it depends on, which pays once minds and skills live in folders of their own (step 12). A
  league is played only when the owner asks (step 11).

The owner has decided: Ratings is a top-level screen, linked from the menu, the Arena and the Lab.
A record is never refused or deleted for being old: the screen says which versions and pool it is
evidence about. How well a mind or skill does is an evaluation's reading, never a test. The full
tournament is not run again.

## Where it starts

The first `tournament` and `unseen` records (`assets/evaluations/`) are the 10-hour run imported:
played on `1bacac44`'s source, 107 entrants, 11,342 bouts; Node, core world, `rapier-coordinate`,
120 Hz. The notes, and the Arena's Ratings panel that lists them, are its ratings refitted from the
games (`rating.ts`). Least squares on those ratings:

| Model of an entrant's rating | R² | rms left, Elo | Parameters (identified) |
|---|---|---|---|
| mind | 0.13 | 208 | 10 |
| loadout | 0.47 | 162 | 5 |
| mind + character + loadout | 0.61 | 140 | 17 |
| mind + character + left item + right item | 0.61 | 140 | 16 |
| mind + character + loadout + mind x loadout | 0.81 | 97 in sample, about 122 corrected | 39 |

So minds are compared with kits held alike; each hand's item, barely tested by the set (left hand
only empty or buckler), is varied by design (step 9); and ratings stay per entrant, the residual
being above an entrant's own uncertainty (median 95 % interval 126 Elo).

Of the rows' 11,726 bouts (384 of them the unseen report's), 7,409 (63 %) end at the 120 s cap,
taking 247 of 310 simulated hours; there the bars decide (`Duel`, `src/arena/duel.ts`), under 0.05
apart in 3,123 and both full in 837. Step 6 reads what the margin and a shorter cap give.

## Design

### Evaluations

`src/evaluation/` is browser-safe (no `node:`, DOM or `process`) and computes with
`src/core/math/real.ts` (its `exp`, and a log it gains), so Node, workers and the screen run one
path to the same result. A module that builds a case's world joins `WORLD_BUILDERS`
(`tests/core-boundary.test.mjs`); each case kind says whether it is bit-equal between engines
(`exact`): bouts are, falls not yet. An evaluation is a **case module**
(`src/evaluation/<id>/cases.ts`: conditions, world, reading) and a **description**
(`<id>/index.ts`: title, question, figures, analysis, default subjects), which imports the case
module and which nothing a case plays imports. A case module plays a core task (`src/core/tasks/`)
where one exists. `EVALUATIONS` (`src/evaluation/evaluations.ts`) is the one catalogue. An
evaluation reads every record of its own: a reading's changed shape is read by its figures, or
takes a new id.

| Type (`src/evaluation/evaluation.ts`) | Shape |
|---|---|
| `Json` | plain finite JSON: what survives a key, a record, a URL and `postMessage` |
| `Subject` | `{ id, label, parts, value: Json }`; `id` stable and readable; `parts` by id with each one's content, e.g. `mind:duellist`, `model:workshop-rogue`, `left:buckler`, `right:sword`; a mind or chooser named by data, resolved through its catalogue |
| `CaseWorld` | `{ kind: "bout", engine, recipe: DuelRecipe, tape: OrdersEntry[] }`, `{ kind: "point", …bout's fields, step, horizon }`, `{ kind: "fall", engine, fall: FallCase }`; one builder each in `playCase`, a `never` default |
| `Reader<R>` | `afterStep()`, `ended`, `reading(): R` |
| `Cases<C, R>` | `arity: 0 \| 1 \| 2` (decision points, a battery, a contest with the first on the left); `play: Json` (the protocol, frozen, in every key); `conditions: C[]`; `world(values: Json[], condition, engine): CaseWorld`; `read(built: BuiltCase): Reader<R>` |
| `Figure<R>` | `{ name, unit, kind: "rate" \| "mean" \| "median", better: "higher" \| "lower", of(reading): number \| boolean \| null }` |
| `Evaluation<C, R>` | `{ id, title, group: "fighters" \| "skills" \| "decisions", question, cases, analysis: Json, subjects(choice: SubjectChoice), figures }`; `analysis` (figure settings, default panel, renamed ids) is in no key; a mind's JSON config gives one subject per character and loadout it fits; a contest's reading carries `score` (0, 0.5, 1 for the left) and `margin` (left bar less right at the end) |

### Case identity

A case's row is reused while nothing it plays has changed. **The key** is the digest of
`{ evaluation, play, engine, world, seconds, code }`; the world holds every subject's value and
every mind's config in full and no index or label, so adding a subject changes no other key, and a
built-in preset's earlier value plays again at current code as a JSON mind.

| Stage | A case's `code` | Kept | New rows |
|---|---|---|---|
| by directory (step 3, `environmentOf`) | the environment: `hashBuildInputs` over what `currentBuildIdentity` (`scripts/build-identity.mjs`) reads, less `scripts/`, `research/`, `tests/harness/`, the pages, `src/ratings/`, the descriptions, `assets/evaluations/` and the notes | a document, script, research file or description edited | anything else under `src/` or `assets/`: a new environment |
| by code (step 12, `caseCode`) | the environment by closure, plus each named mind kind's own code | also an analysis setting, a screen, one entrant (for cases without it), the lists of entrants and evaluations | the toolkit's play code or data: a new environment and pool; an entrant: its own cases |

- **The environment by closure**: SHA-256, files hashed as `hashBuildInputs` does with line endings
  normalised, over the static import closure (JSON included) of `src/evaluation/play.ts` and the
  case module, cut at the cut points (step 12), and the lockfile, vendored solver and installed
  Rapier files. It is about 250 files, and through `src/core/mind/catalog.ts` and
  `src/core/models.ts` (whose humanoid default is `OPTIONS`) holds the built-in minds, every skill
  and every preset in `src/core/mind/config.ts`: editing one is a toolkit change. Only `direct`
  and `tempo` are entrants, so the cut saves little until step 12.
- **A mind kind's own code** is its entry's closure less the environment: an entrant's folder and
  `assets/entrants/<kind>/`, or a built-in kind's entry module (controller, slots, fields).

### Cases, schedules and comparisons

The runner makes the cases, `{ subjects, condition, world, seconds }`: arity 0, each condition;
1, each subject on each; 2, each scheduled pair on both sides and every condition. Schedules:
`all` (every pair); `versus { panel }` (every subject against every member); `sparse { opponents,
seed }` (each subject meets the `opponents` others with the lowest draw of the digest of the sorted
pair and the seed; as a union, between `opponents` and about twice as many). The unit of evidence
is a **pair**, one condition with each side on the left, never split between a verdict and a gap.
Pairs run in a seeded shuffle, and a verdict or table reads only the longest complete prefix, so it
depends on neither lane count nor finishing order.

| Comparison | Question | Answer, in the task's units |
|---|---|---|
| `head-to-head A B` | does A beat B? | mean of A's pair scores against B less one half; mean of A's pair margins |
| `panel A' A` | does A' do better against the panel? | mean over the panel's pairs of A' less A on the same member and condition; A's rows may come from a record in the pool |
| `battery A' A` | is A' better at the task? | each figure's paired difference over the conditions both played |

The report gives each comparison asked (a version can beat its parent and do worse against the
panel), with per-member and per-condition differences, the worst matchups, the stalemates (bouts
at the cap with both bars full, bouts with no blow) and the conditions one side alone played.
**Stopping** (`--until settled`) is a sequential test on a comparison's mean stopping figure,
bounds in its units, error rates `alpha` and `beta`, and a budget of pairs. A contest stops on score
per pair (bounds e.g. 0 and 0.05) until step 6 chooses; variance is regularised by one pair at each
extreme and a minimum count of pairs, so early wins cannot settle it. It ends **better**, **not
better**, **inconclusive** at the budget, or **incomplete** for a missing pair of a retriable
fault. An interval names what it covers: pairs of the named conditions and panel, at their code.

### Faults and records

- A row is `{ key, reading, digest, fault }`. A case's own error is a `fault` row, a non-finite
  state an `invalid` one: results, recorded and reused. A worker's death or the watchdog
  (`--case-minutes`, default 30) is reported, retriable, and leaves the row missing. A missing row
  stops the analysis; a comparison with a fault row in its prefix says so.
- **Working rows**: `research/runs/evaluations/<id>/<shard>.jsonl`, every file in the folder read,
  so machines merge by copying; found by key. Two rows with one key that disagree in reading,
  digest or fault stop the run, naming both.
- **Records**: `npm run evaluate -- <id> --write` writes
  `assets/evaluations/<id>/<yyyy-mm-dd>-<commit8>-<keys8>.jsonl` (`keys8` digests its case keys),
  refused when a file of its cases' code differs from its commit or is untracked, when the name
  exists with other content, or when a row is missing. Records hold games and are never rewritten;
  tables and ratings are derived when read and name their analysis settings. A key whose readings
  differ across records is refused.
- **Header line**: `recordingIdentity(BUILD_IDENTITY, "evaluation/1", { engine, harness, play })`,
  commit, date, harness, schedule; the pool's protocol and environment digests; each subject in
  full with, for it and each part, version and parent. **Then a line per case**: `{ subjects,
  condition, key, code, world, reading, digest, fault }`; the world opens the case without its
  definition.

### Versions, pools and ratings

- **`{ id, version }`** names everything rated: a subject and each part (mind, character, item in a
  hand). Ids are stable and readable: `duellist/workshop-rogue/buckler,sword` (an entrant),
  `mind:duellist`, `model:workshop-rogue`, `right:sword`; a JSON mind is its own id until adopted
  as a preset; renames go in `analysis.renames`.
- **A version** is the digest of its pool and its own content: a mind's config and its kind's own
  code (in the environment until step 12), a character's `BodySpec` as its model builds it, an
  item's `ItemSpec` (`heldItem`, `src/core/items/held.ts`), an entrant's parts together. Nobody
  bumps it. Its `own`, `protocol` and `environment` digests are stored apart, so the screen says
  which changed from the parent, and labels it `duellist v3 (2026-10-24, 5f1c09ab)` by its order in
  the id's history and first record.
- **The parent** is the one named with `--previous` when a version first appears in a record, or
  none; dates never decide. If history proves thin, the default becomes the same id's version in
  the newest record on the branch's first-parent history (`git log --first-parent` over
  `assets/evaluations/<id>/`). Parents form a graph (a revert is the earlier version; two branches
  can reach the same content); the screen shows each edge, orders a series by first appearance in
  first-parent history, and refuses nothing. A comparison names its baseline apart, often the
  parent.
- **A pool** shares a protocol and an environment; its versions are compared directly, and no
  strength is carried across pools. A skill's code is environment until it has a folder of its own
  ([Component registration](2026-10-21-component-registration.md)), then enters a case's code as a
  mind's kind does.
- **Ratings within a pool** (`src/evaluation/rating.ts`: `bradleyTerry` and `ratingIntervals` on
  `real.ts`): one strength per `{ id, version }` over the pool's distinct
  keys, `P(i beats j) = 1 / (1 + 10^((s_j - s_i) / 400))`, a draw half a win, a drawn half-game
  prior and pair bootstrap. An entrant shows its rating and interval, its score per opponent and
  worst matchups. Minds, characters and items are compared on common ground (two minds by their
  entrants' paired results on kits both fit, coverage beside, never averaged in), items, characters
  and attributes first from step 9. Across pools a subject's history is a series: its standing in
  each pool, each version's panel comparison with its parent, the changes between pools. A battery
  needs no model: its change from its parent is the paired difference over shared conditions.

## Steps

Each is a toolkit change. Steps 1 to 4 have landed (`src/evaluation/`, `npm run evaluate`, the
match, the tournament and the unseen report as evaluations, ratings within a pool, the 10-hour run
imported). Steps 5 and 6 choose on bouts played
under the one movement pipeline (`travelSpeed`). Later steps run when their question is asked;
12 when it would save something; 14 when the screen is in use and a live run would save a trip to the CLI.

### 1. Secure the 10-hour rows

`OUTPUTS` (`scripts/build-identity.mjs`, an exact-name `Set`) becomes a prefix test covering
`assets/evaluations/`. The tournament machine's
`research/runs/tournament/d5041a87…-76b07355f926f9df.jsonl` (about 10 MB, with the unseen report)
is copied unchanged to `assets/evaluations/imports/tournament-1bacac44.jsonl`, beside
`tournament-1bacac44.json`: commits `1bacac44` (run) and `d06fb568` (table), build identity,
protocol, harness, engine, the file's SHA-256.

Check: 11,342 and 384 rows, 7,409 at the cap. Committed on its own.

### 5. The panel report: a change against its previous version

- The comparisons and `settled` stopping; the CLI's `--against`, `--until settled` and `--budget`.
- The default panel in `tournament`'s analysis: about eight opponents varied across minds,
  characters and loadouts, chosen for variety (not strength) from the 10-hour record, with
  reasons in the commit message.
- Cost: eight members x four conditions x both sides = 64 bouts, about 3.5 minutes at the 10-hour
  run's desktop rate (about 19 a minute), twice that when the previous version replays in a new
  pool. The CLI prints its estimate first; `--budget` defaults to about 10 minutes.
- `npm run evaluate -- tournament --mind new.json --previous duellist --until settled --budget
  <pairs>` answers in score and margin per pair: head-to-head; against the panel, with the previous
  version's rows from the newest record in the pool; per-member and per-condition differences,
  worst matchups, stalemates. After an environment change (a built-in preset's change is one, its
  previous value playing as a JSON mind), the previous version and the panel replay in the new
  pool. Skill batteries (step 10) answer the same way, by figure.

Check: `versus` pairs exactly the panel, both sides, the same for a seed; on scripted pools, error
rates over 2,000 runs at each bound fall within `alpha` and `beta` plus sampling error, four early
wins don't settle, the budget gives inconclusive, a missing pair gives incomplete, and recorded rows
answer as live ones.

### 6. The margin and the cap

- Margin, on the imported rows: for entrant pairs about 50, 100 and 200 Elo apart, resample their
  bout pairs and run step 5's test on score and on margin at equal error rates, reading how often
  each reaches the full run's sign and in how many pairs. Margin becomes a contest's stopping
  figure if it is right as often in fewer pairs; score is reported beside it either way.
- Cap, from bar series of rows the first paired reports play, once there are enough
  (no league played for it; reports play at 120 s until then). For 30, 45, 60 and 90 s: the share
  of bouts whose outcome there (an earlier ending, else the bars' leader) is their 120 s outcome;
  the share of subject and panel-member matchups keeping their standing (sign of mean pair score);
  simulated time per pair.
- The rating protocols' cap becomes the shortest keeping at least 95 % of matchups' standing, or
  stays 120 s: a new protocol, so a new pool. `CAP_SECONDS` does not change. Tables and choice go
  in the commit message.

Check: the bar series' last entry equals the reading's bars.

### 7. The Ratings screen: browse and history

- Route `ratings`: `Route`, `routeFor` (`src/app-route.ts`), `modules`, `open()` (`src/app.ts`), a

- Evaluations by group (Fighters, Skills, Decisions), each with its question. A contest shows its

- The Arena's Ratings button opens `?play=ratings&evaluation=tournament`; its panel,

Check: the gate with `npm run build`.

### 8. Watch a case

A bout case opens at `?play=arena#case=<world JSON>` (recipe, tape, engine): `bootArena` separates
assembling a recipe from the address from `begin`, the pickers show the case's choices, Back

it. A point case opens at its step from the stored tape. Imported cases are not opened; fall cases
wait for bit equality (step 13).

Check: the gate with `npm run build`.

### 9. Items, characters and attributes, by design

Each factor is varied with all else held, against reference minds (the panel's that fit, about
three), when its question is asked (an item added or changed, a character's or attribute's
balance), on the subjects it names, within budget; nothing plays the whole catalogue.

| Evaluation | Subjects | A case | Gives |
|---|---|---|---|
| `loadouts` (arity 2) | `LOADOUTS` (`src/core/items/held.ts`), each hand's item a part | two loadouts, one mind and character both sides; conditions: reference minds, characters, gaps where both fit (`modelHolds`, `modelSupportsMind`) | a rating per loadout; the loadout grid (items' balance report); each hand's item by paired swaps of loadouts differing in one hand, same opponents |
| `characters` (arity 2) | `BODY_MODELS` (`src/core/models.ts`) | two characters, one mind and loadout both sides, over reference minds, loadouts, gaps both fit | a rating per character |
| `attributes` (arity 1) | entrants | an attribute (`balance`; `haste` where `modelHastes` allows), value, gap, side: the entrant at that value against itself at its character's own, through `DuelRecipe`'s `balance` and `haste` | score and margin by value: a curve, slope in Elo per 10 % by the rating's logistic; values from the game's range, in the commit message |

The screen shows a mind's attribute curves beside its loadouts' ratings on one character, in one
Elo scale; no budget of points is built here.

Check: loadout and character cases mirror all but their subjects; conditions skip what does not
fit; an attribute case at the own value plays to the mirror bout's digest.

### 10. Skills: batteries and ablations

- Batteries: `src/evaluation/blade/`, `buckler/`, `court/` take the cases, readers and summaries of
  `research/blade-task.mjs`, `buckler-task.mjs`, `court-task.mjs` (models x styles x marks; models x
  angles x at x own; models x gaps x sides x targets), which go. Subjects are what each compares
  (striker's executor tuning, defender's cover, approaching mind); each plays its core task where
  one exists; angle-built orders use `real.ts`; the harness is named from the engine played (they
  print "Rapier" while running `rapier-coordinate`).
- Ablations: step 5's panel comparison of a mind against itself with one `SkillKit` slot
  (`src/core/mind/config.ts`: locomotion, guard, support, an executor or an action) replaced, or
  emptied where allowed (`support: null`, an action removed), as a JSON mind;
  `--ablate <slot>=<config JSON>` builds it from `--previous`. Each selectable alternative of a
  skill is an ablation. The screen shows battery beside ablations; a battery gain with no gain in
  fights is a finding.
- Other research batteries (`research/locomotion-run.mjs`'s gait battery among them), and the
  capabilities `tests/*-capability.test.mjs@2a1b29ac` read, become batteries when next worked on.
  `docs/reference/sword-and-buckler.md` names its stages' evaluations and protocols, its figures
  read again before compared.

Check: `npm run evaluate -- blade`, `buckler` and `court` give, for the reference subject, the
summaries `research/blade-task.mjs`, `buckler-task.mjs` and `court-task.mjs` give at the commit
before.

### 11. The sparse league, when asked

Only when the owner asks, after step 12, within the owner's budget, playing only cases no kept row
holds. `sparse` at step 6's cap. `opponents` is chosen with no bout played: on the imported games,
8, 16 and 32 on five seeds by subsampling, reading rank correlation with the full run, largest
rating gap, bouts, and held-out log-loss; the default and table go in the commit message. Shared
factors (mind, character, each hand's item, with an entrant term) join the fit only if they lower
held-out log-loss at that `opponents` and their intervals cover held-out games at their stated
rate; otherwise one strength per entrant, readings given either way, checked against step 9.

Check: `sparse` gives each subject between `opponents` and about twice as many, the same for a
seed.

### 12. Case identity by code

Starts when the first built-in mind or skill has a folder of its own
([Component registration](2026-10-21-component-registration.md)) or entrants are most of the field;
it lets rows outlive unrelated changes.

- Cut point one, the kinds list: `OPTIONS_MIND`, `FIGHTER_MIND` and `QUADRUPED_MIND`, with slots
  and fields, move into modules of their own like `TEMPO_MIND` (`src/core/entrants/tempo/mind.ts`);
  `src/core/mind/kinds.ts` imports and lists every kind's controller and nothing else;
  `controllers.ts` keeps `registry`, `controllerOf` and the fit and fault checks over it. Cut point
  two, `src/build-identity.ts`: its value is the whole tree's (recordings stamp it), so a row holds
  no recording, save or tape identity.
- `caseCode` and the closure walk replace `environmentOf` in `scripts/build-identity.mjs`; the walk
  of `risingImplementation` (`research/rising-provenance.mjs`) moves there and it builds on it. The
  Vite plugin `recording-build-identity` emits a file table of hashes and import edges, the
  browser's twin, which `src/build-identity.ts` exports.
- Mind data loads through a store ([Mind data](2026-10-21-mind-data.md)), so a case's code adds the
  files `treeData` names for each mind its world names.

Check: the fingerprint compares clean. The closure walk refuses a kinds list of more than imports
and the array (TypeScript's parser) and a non-literal dynamic import in any closure; in a scratch
copy, a description, `src/arena/main.ts`, `scripts/build-identity.mjs` or a kinds-list line edited
changes no key, one entrant's file only its cases', `src/core/mind/fighter.ts` every case's. The
commit message gives the environment's file count and what each kind adds.

### 14. Run live (waits)

This waits until the screen is in use and a live run would save a trip to the CLI.

- `src/ratings/case-worker.ts` plays cases with `playCase`; `src/ratings/pool.ts` is the browser
  `spawn()` for `lanes.ts`; each worker calls `loadData` for its cases' mind data.
- The identity plugin emits the hashes `environmentOf` reads (or step 12's table) and also applies
  to workers (`worker.plugins`, `vite.config.ts`, whose comment that only the bench makes a worker
  is corrected).
- The run panel picks evaluation, subjects (a mind from the mind editor by its link config),
  schedule, comparison, budget and lanes (default `navigator.hardwareConcurrency - 2`); reuses rows
  of records whose case code matches; updates rows, table and answer as the prefix completes. A
  live run is unrecorded: its rows save as a working-rows file, and the panel shows the command
  that writes the record.

Check: in a browser, a live case's digest equals Node's for the same case.
