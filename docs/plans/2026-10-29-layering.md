# Layering: no layer holds the one above it, and one way into a body

## Why

The owner wants every layer general: nothing ad hoc, nothing hard-coded to one mind or one body,
and tactics one implementation among others, not a concept the toolkit is built around. A sweep of
`src/core/` for imports that point up the stack found these:

- **The skills hold the layer above's memory and report.** `skillSet` (`src/core/skills/arbiter.ts`),
  `recipeSkills` (`skills.ts`), `combatSkills` (`combat.ts`) and `fighterSkills`
  (`src/core/mind/fighter.ts`) take the tactics' `state` and `engagement`; the skill set keeps the
  first in its state (`state.tactics`) and republishes the second (`SkillReport.engagement`, typed
  `Tactics["engagement"]`), so that a fork copies a mind's memory and a readout finds its report.
- **The toolkit's seam is named for one implementation.** Whatever decides a body's intent plugs in
  as `Tactics` (`src/core/mind/tactics.ts`, `driveBy`, `MindWiring.script`, `Controller`); Kinetic's
  chooser is a `Tactics`. The same file holds every mind's report (`Engagement`, its `candidates`
  and `pending` typed from `action-tactics.ts`) and Kinetic's chooser's offers (`Offer`).
- **One file holds three layers' configs.** `src/core/mind/config.ts` holds the skills'
  (`ActionConfig`, `ExecutorEntry`, `MOVE`, the gaits' `LocomotionConfig`), the tactics'
  (`BehavioursConfig`, `FIGHTING`, the focus, condition and selector rules) and the minds' (the
  presets; `SkillKit` is a `Pick` of `FighterConfig`), so skills import the minds' presets file.
- **The general contracts know the fighter.** A drill drives a mind by tactics parts
  (`drill-tactics.ts`, `drill-gait.ts`, `TacticsPart`), so Kinetic carries a `scripted` option of
  tactics (`options/kinds.ts`) and builds its skills through `prepareTacticsSkills`; a
  controller's script hook is typed by the fighter's config (`Scripted`,
  `src/core/mind/controller.ts`: "a mind that takes a script has a fighter's slots"); the toolkit's
  part lookup and catalog name the tactics roles (`lookup.ts`, `catalog.ts`), and its action
  estimates and making context sit in the tactics files (`ActionEstimates`, `TacticsMaking`).
- **The body hosts minds one shape at a time.** The command layers (`commandMind`,
  `src/core/body.ts`) read a left and a right fist, a head and a two-footed stance, and refuse any
  other body (`commandRefusal`), so the quadruped writes its own host (`src/core/reptile/mind.ts`).
  A mind takes a body three ways (`BodyHost.command`, `hosted`, `policy`), each built apart. The
  body itself hands control to sub-minds (`BodyOptions.subs`, `hosting`): a second way of
  deciding, below the mind and outside its chooser, which Kinetic does without (`subs: []`). Motor
  control, the body and the skills name about 57 humanoid segments (`foot.`, `hand.`) outright, and
  the humanoid's support ends (`BodySpec.ends`) and the quadruped's (`effectors[].support`) are two
  fields for one thing.
- **Smaller misplacements**: the body's ground reading in the rise's folder (`groundReading`,
  `src/core/mind/ground/reading.ts`, read by `body.ts`); a learned policy's vocabulary in `mind/`
  (`learnerOf`, `mind/learner.ts`, read by `skills/straight-punch.ts` and `entrants/bare/mind.ts`);
  the data store typed by one skill's policy (`PunchPolicy`, `src/core/data/store.ts`); a segment's
  turn in control, read by the rules and twelve others (`turnOfToRef`, `control/support.ts`); a
  friction constant in the read view's module (`CONTACT_FRICTION`, `read-body.ts`).

**The owner's decisions** (2026-10-29): everything general, with no ad-hoc hard-coded hacks;
tactics tucked away in their own implementation package, not a top-level concept.

**Decided here, which the owner may reverse**: the seam's name, `Decider`; the tactics package at
`src/core/mind/tactics/`, holding the fighter kind and its presets; a body's view and motor read
from its spec rather than from named humanoid segments.

**What must not move**: every humanoid bout, Crypt run, fall and Lab scenario, bit for bit, through
step 8 (`scripts/fingerprint.mjs`); the gate (`npm test`) at each step. Step 9 moves the quadruped
and is measured.

## The shape

| Layer | Knows | Never knows |
|---|---|---|
| A body (`embody`, the one way in) | its muscles, assist, hands, the body as read, its senses, its contact labels, after-physics | who drives it, or how |
| The command layers (a toolkit layer any mind may build on its body) | motor control, a view read from the spec, being released and resumed | the skills, the decider, sub-minds |
| The skills (`skillSet`) | the command layers, navigation, an `Intent` in | the decider's memory or report |
| A decider (`Decider`: tactics, Kinetic's chooser, a drill's script, a person's keys) | the skills' report and its own memory | anything of another decider |
| A mind | its decider, skills, command layers and any sub-minds, put together; its memory, report and who has the body, assembled by it | the host's world |

The registries that list each kind (`mind/kinds.ts`, `controllers.ts`, `lookup.ts`, `catalog.ts`,
`src/core/models.ts`'s default minds) are where the layers meet, and import every kind by design.

## Steps

Each lands green on its own: `npm run check`, `npm test`, `npm run build` where browser code moves.

- **The fingerprint, a step at a time**: `node scripts/fingerprint.mjs --json` at the commit
  before, `--compare` at the step. A file moved changes the environment digest and each case's
  code identity, which is expected; the outcomes do not move. Its printed line holds no state, and
  `--compare` reports a state reshaped without failing; nothing keeps a saved state across
  commits, so a state's shape may move.
- **What a move also updates**: the build identity's role paths (`CUTS.roles`, `CUTS.store`,
  `scripts/build-identity.mjs`), the boundary test's adapters (`MIND_ADAPTERS`), the fingerprint's
  own imports, and the architecture's sections the step makes wrong.
- **Commits**: a step that touches the toolkit and an entrant lands as two commits, the toolkit's
  first (`node scripts/entrant-check.mjs`), or as one named mixed where the toolkit's alone would
  not build.

### 1. The skills hold nothing of the layer above

- `skillSet`, `recipeSkills`, `combatSkills` and `fighterSkills` take no tactics argument; the
  skill set's state drops `tactics`, and `SkillReport` drops `engagement`.
- A mind assembles its own memory and report: `createFighter`, `driveFighter`, Kinetic's
  `createKinetic`, Vanguard's, the drill opponent's and the Lab's scripted drive return
  `state: { skills: skills.state, decider: decider.state }` and a `MindReport` whose `engagement`
  is the decider's (`skillsReport(skills, decider)`, `src/core/mind/minds.ts`). `driveBy` returns
  both.
- Every reader of `skills.report.engagement` reads the mind's report instead
  (`MindMade.report.engagement`): the Arena's readout and HUD (`src/arena/fighter-readout.ts`,
  `fighter-hud.ts`, `main.ts`), the drills' readers (`src/evaluation/strike/read.ts`,
  `gait/read.ts`, `cover/read.ts`), the Lab (`src/lab/attack-mode.ts`, `attack-scenario.ts`), the
  action readout (`src/ui/action-readout.ts`), the tests that read it
  (`tests/tactics-contract.test.mjs`, `entrant-vanguard.test.mjs`, `lab-targets.test.mjs`) and the
  research scripts (`research/arena-combat.mjs`, `ground-combat.mjs`).
- **The fork case** in `tests/mind-contract.test.mjs` forks Kinetic alone; it forks each mind kind
  instead, a short bout each, under 10 s together. It catches the class this step risks: a mind
  whose memory falls out of its state and does not fork.

Check: the gate; the fingerprint's outcomes unchanged.

### 2. A neutral seam, and the reports apart

- `Decider<S = Sight, I = Intent>` (`src/core/mind/decider.ts`): `name`, `decide(sight, dt)`,
  `state`, `engagement`; `Sight` and `driveBy` with it. `MindWiring.script`, `Controller` and
  `Scripted` name `Decider`. `Tactics` is gone as a toolkit name.
- `src/core/mind/engagement.ts`: `Engagement`, `EngagementDetail`, `engagementWithDetails`, and the
  readout's own types of what a decider weighed (`Offer`, `OfferTerms`, and a candidate and its
  pending action, which `action-tactics.ts` then fills). No readout type names a decider's module.
- `TacticalDecision` goes to the tactics package with step 3.

Check: the gate; the fingerprint's outcomes unchanged.

### 3. Tactics as a package

`src/core/mind/tactics/`, an implementation of `Decider`: `tactics-part.ts` (`TacticsPart`,
`tacticsOf`, `prepareTacticsSkills`), `planners.ts`, `action-tactics.ts`, `behaviours/`,
`behaviours.ts`, `behaviour-part.ts`, `stand-tactics.ts`, `script-tactics.ts`, `TacticalDecision`,
and the fighter kind built on them: `createFighter`, `driveFighter`, `FIGHTER_MIND`
(`fighter-kind.ts`), its faults.

- **What stays in the toolkit**, under names that say what it is: what a decider is made from
  (`TacticsMaking` as `DeciderMaking`, and `ActionEstimates`, which `action-config.ts` and
  `executor-part.ts` read); the body layer from a kit (`fighterSkills` as `kitSkills`), the body's
  options from a mind's parts (`fighterBody` as `kitBody`), `kitFaults`; `action-producer.ts`
  (the ground fight's, `ground/ground-fight.ts`), `ordered.ts` (Kinetic's following orders) and
  `targets.ts` (the skills', the ground's and the quadruped's), which the architecture's layer
  table corrects.
- Vanguard, the Lab's scripted drive and the registries import the package.

Check: the gate; the fingerprint's outcomes unchanged.

### 4. Each layer's config with its layer

`src/core/mind/config.ts` keeps the minds' configs that no package owns, and the registries' unions:

- the skills' (`ActionConfig`, `ExecutorEntry`) in `src/core/skills/configs.ts`, an action's aim a
  `PartConfig` (the union of aims, `AimConfig`, staying with its registry, `mind/aims.ts`); `MOVE`
  with its part (`skills/move-part.ts`); a gait names its legs as a `PartConfig`
  (`skills/gaits.ts`), the union of every legs kind (`LocomotionConfig`) staying with its registry
  (`mind/locomotions.ts`);
- `SkillKit` declared on its own fields (legs, navigation, guard, support, executors, actions,
  motor), not a `Pick` of `FighterConfig`;
- the tactics' (`FocusRuleConfig`, `ConditionConfig`, `SelectorConfig`, `BehaviourConfig`,
  `BehavioursConfig`, `TacticsConfig`, `FIGHTING`), `FighterConfig` and the fighter presets
  (`RECIPE_FIGHTER`, `CLASSIC`, `PUNCHER`, `COUNTER_PUNCHER`, `BEHAVIOURS`, `DUELLIST`) in the
  package (`tactics/config.ts`), which `src/core/models.ts` (a model's default mind) and the
  research tasks (`src/core/tasks/support-entry.ts`) import;
- the quadruped's (`QuadrupedConfig`, `QUADRUPED` and its parts' unions) in `src/core/reptile/`.

Check: the gate; the fingerprint's outcomes unchanged.

### 5. Drills and scripts drive any mind by a decider

- A drill's script is a `Decider` made from a `DeciderMaking`, not a tactics part: `drill-tactics.ts`
  and `drill-gait.ts` become scripts (`src/core/mind/scripts/`); a drill's `fight` phase is the
  mind's own decider, which the script holds and hands the body back to. The Cover drill's script
  stays Kinetic's (`entrants/kinetic/drill-cover.ts`, built from Kinetic's chooser, covers and
  walker), a part of the script role.
- A controller's hooks are general: `drilled(config, script)` and `drilledBy` place a script in any
  mind (Kinetic as an option wrapping a decider, `scripted` in `options/kinds.ts`; the fighter as
  its tactics), and `Scripted` takes a `Decider` and the mind's own config type, not
  `FighterConfig`. What a script asks of the skills it is driven over (`prepareSkills`) is the
  script role's own hook.
- **The boundary**, added here, once nothing but its own minds reaches the package: a rule beside
  `COMMAND_BARRED` in `tests/core-boundary.test.mjs`, with its control case, that no file under
  `src/core/` outside the package imports from it but the fighter kind's users (Vanguard, the Lab's
  scripted drive in `src/lab/`, which is outside the core) and the registries named above.

Check: the gate, with the new rule and its control; the fingerprint's outcomes unchanged, the
drills' cases with it.

### 6. One way into a body; the command layers a toolkit layer

- **One way in**: a mind takes its body through the host once (`BodyHost.take`), as a `Mind` made
  from its `OwnBody`, which gains its senses, its contact labels (`contactIdentity`, a grant today
  passed through `host.ts` and `fighterBody`) and an after-physics hook (`afterPhysics`, today
  wired by hand inside `createBody`). The host builds the fight's `PhysicalBody` the same way for
  every mind; who has the body (`PhysicalBody.has`) is the mind's (`Mind.has`, `hosting`'s where a
  mind hands its body over, else its name), the names it reports unchanged, since readouts, the
  Lab's ground meter and the fingerprint's down meter print them. `BodyHost.command`, `hosted` and
  `policy` go.
- **The command layers** (`commandLayers(own, options)`, `src/core/control/command-layers.ts`): a
  `HostMind` (look, act, release, resume) any mind builds on its own body, with motor control from
  the mind's motor part and a view; it returns the `Body` its drivers have. The policy mind
  (`createPolicyBody`, `mind/direct.ts`) is a `Mind` over `OwnBody` the same way.
- **A body built outside a fight** (a test, a research script, a task) is built through the same
  way by one toolkit function, `commandedBody(built, world, options)`, which takes what
  `createBody` takes and returns what it returns: `tests/harness/` (`combat-combination.mjs`,
  `garbage.mjs`, `probes.mjs`), `tests/mind-contract.test.mjs`, `swap.test.mjs`,
  `scripts/fingerprint.mjs`, `src/core/tasks/reach.ts`, `src/evaluation/rising.ts`,
  `technique.ts`, `fall.ts`, `src/lab/actor.ts` and the research scripts change an import;
  `src/core/tasks/posture-hold.ts` builds its policy body the same way.

Check: the gate; the fingerprint's outcomes unchanged; in a browser, an Arena bout, a Crypt run and
the Lab's stand-up scenario look as they did.

### 7. Sub-minds out of the body

- `BodyOptions.subs` goes. A mind that hands its body over builds `hosting` (`mind/sub-mind.ts`)
  over its own command layers and its sub-minds: the fighter kind and Vanguard with `STAND_UP` and
  `lie`, and the harnesses that pass sub-minds (`src/evaluation/rising.ts`, `technique.ts`,
  `fall.ts`, `src/lab/actor.ts`, `lab-scenario.ts`, `ground-config.ts`, `ground-scenario.ts`,
  `main.ts`, `tests/fixtures/swap/mind.mjs`).
- **The order is kept**, so the steps are the same to the bit: the command layers, then the
  sub-minds, made before the view's first look; the sub-minds' after-physics listeners (the
  ground fight's own skill set, `ground/ground-fight.ts`) registered before the skills'. The
  command layers' sub-mind flag (`subOwned`, which turns the ground reading on, `body.ts`) is their
  being released, as they know it, under the same rule.
- `SubMindMaker` (`mind/kit.ts`) takes what a mind hands it, the command layers' view among it,
  never the body module.

Check: the gate; the fingerprint's outcomes unchanged, the falls and stand-ups with it.

### 8. Motor control and the view read from the spec

- **One field for support ends**: the spec's `ends` (`BodySpec.ends`, `BearingEndSpec`), which the
  humanoid's stance and rise read; the quadruped's paws become `ends` and `effectors[].support`
  goes (a spec change; the humanoid's spec unchanged).
- **The view**: the striking points the spec names (each effector with a `knuckles` point, keyed
  by its segment) in place of `fists.left` and `fists.right` (11 reads in 10 files); the point
  strikes are ranged from (`view.head`, about 69 reads in 16 files) read from the mark the spec
  names for it (`BodySpec.marks.high`); the stance over the spec's support ends.
- **Motor control and the stance** name no segment: the segments `control/` and `body.ts` name
  (`foot.left`, `hand.right` and kin) are read from the spec's effectors and ends. A skill that
  needs a hand or a foot names it in its config, as the actions do, and refuses a body without it
  by its `fits`; `commandRefusal` and `commandable` go, their readers (`ground/technique.ts`'s
  `fitsHumanoid`, `src/evaluation/fall.ts`, `takesCommands`) asking the parts' fits.

Check: the gate; the fingerprint's outcomes unchanged (the humanoid's segments read from its spec
are the ones named today).

### 9. The quadruped on the command layers

- Its support motor (`SupportMotorPart`, `reptile/parts.ts`, `make(own, paws, config)`) becomes a
  part of the motor role (`MotorMaker`) over the spec's ends, carrying what the command layers ask
  (effectors, points, stance over its ends).
- Its host (`reptile/mind.ts`) goes: it builds the command layers over its body, its view from its
  spec (its paws the support ends, its jaw an effector), and its gaits, bite and tactics as skills
  and a decider over them, as a humanoid's.

Check: the gate; its fingerprint cases move, and are read before and after on its own bouts
(`npm run match` against the same opponent, both sides); the owner watches a bout.

### 10. The smaller misplacements

- `groundReading` beside the view's other readings (`src/core/control/`).
- `learnerOf` and `Learner` with the learned skills (`src/core/skills/learner.ts`), for the punch
  and the bare entrant.
- The data store typed by what each key's reader declares, not by one skill or `mind/profile.ts`,
  its module still parseable as the build identity's store file (`CUTS.store`).
- `turnOfToRef` beside the read view it reads (`read-body.ts`), its thirteen importers (`src/audio`
  among them) changing an import.
- `CONTACT_FRICTION` in a spec module the engine and control both read (`src/core/spec/`), since
  the engine's folder is barred to control (`MIND_BARRED`).

Check: the gate; the fingerprint's outcomes unchanged; the sweep's script, run once in `.tmp/`,
finds no import up the stack but the registries.

## Done when

No layer imports or holds anything of a layer above it but the registries that list its kinds;
every mind takes its body one way and builds what it uses over it; the command layers read their
body from its spec, name no segment, and the quadruped stands on them; tactics are a package
nothing but the minds built on it and the registries import; and every humanoid case plays as
before, bit for bit.
