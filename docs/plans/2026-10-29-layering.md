# Layering: no layer holds the one above it, and one way into a body

## Why

The owner wants every layer general: nothing ad hoc, nothing hard-coded to one mind or one body,
and tactics one implementation among others, not a concept the toolkit is built around. A sweep of
`src/core/` for imports that point up the stack found these:

- **The skills hold the layer above's memory and report.** `skillSet` (`src/core/skills/arbiter.ts`),
  `recipeSkills` (`skills.ts`), `combatSkills` (`combat.ts`) and `fighterSkills`
  (`src/core/mind/fighter.ts`) take the tactics' `state` and `engagement`; the skill set keeps the
  first in its state (`state.tactics`) and republishes the second (`SkillReport.engagement`, typed
  `Tactics["engagement"]`), so that a fork copies a mind's memory and a readout finds its report.
  The skills' preparation for a script reads the decider's live decision too (`prepareSkills`,
  `TacticalDecision`, `tactics-part.ts`).
- **The toolkit's seam is named for one implementation.** Whatever decides a body's intent plugs in
  as `Tactics` (`src/core/mind/tactics.ts`, `driveBy`, `MindWiring.script`, `Controller`); Option
  Mind's chooser is a `Tactics`. The same file holds every mind's report (`Engagement`, its
  `candidates` and `pending` typed from `action-tactics.ts`) and Option Mind's chooser's offers
  (`Offer`).
- **The part framework belongs to no layer.** `parts.ts`, `fields.ts` and the part lookup
  (`lookup.ts`, which imports every role, the tactics' and the quadruped's among them) sit in
  `src/core/mind/`; motor control imports them (`control/motor-part.ts`), and the skills' role
  contracts (`executor-part.ts`, `locomotion-part.ts`) sit in `mind/` beside the tactics'.
- **One file holds three layers' configs.** `src/core/mind/config.ts` holds the skills'
  (`ActionConfig`, `ExecutorEntry`, `MOVE`, the gaits' `LocomotionConfig`), the tactics'
  (`BehavioursConfig`, `FIGHTING`, the focus and selector rules) and the minds' (the presets;
  `SkillKit` is a `Pick` of `FighterConfig`), so skills import the minds' presets file.
- **The general contracts know the fighter.** A drill drives a mind by tactics parts
  (`drill-tactics.ts`, `drill-gait.ts`, `TacticsPart`), so Option Mind carries a `scripted` option
  of tactics (`options/kinds.ts`) and builds its skills through `prepareTacticsSkills`; a
  controller's script hook is typed by the fighter's config (`Scripted`,
  `src/core/mind/controller.ts`: "a mind that takes a script has a fighter's slots"); the toolkit's
  catalog names the tactics roles (`catalog.ts`), and its action estimates and making context sit
  in the tactics files (`ActionEstimates`, `TacticsMaking`).
- **A mind takes a body three ways** (`BodyHost.command`, `hosted`, `policy`), each built apart,
  and the body itself hands control to sub-minds (`BodyOptions.subs`, `hosting`): a second way of
  deciding, below the mind and outside its chooser, which Option Mind does without (`subs: []`).
- **The body's shape is written into the command layers.** They read a left and a right fist, a
  head and a two-footed stance and refuse any other body (`commandRefusal`, `src/core/body.ts`), so
  the quadruped writes its own host (`src/core/reptile/mind.ts`); the skills name about 80 humanoid
  segments outright (`combat.ts`, `strike.ts`, `kick.ts` and the `*-part.ts` files), and the stance
  is a pair of sides (`StanceGoal.feet`, `anchors`).
- **Smaller misplacements**: the body's ground reading in the rise's folder (`groundReading`,
  `src/core/mind/ground/reading.ts`, read by `body.ts`, reading `lieOf` from `mind/rise/`); a learned
  policy's vocabulary in `mind/` (`learnerOf`, `mind/learner.ts`, read by
  `skills/straight-punch.ts` and `entrants/bare/mind.ts`); the data store typed by one skill's
  policy (`PunchPolicy`, `src/core/data/store.ts`); a segment's turn in control, read by the rules
  and twelve others (`turnOfToRef`, `control/support.ts`); a friction constant in the read view's
  module (`CONTACT_FRICTION`, `read-body.ts`).

**The owner's decisions** (2026-10-29): everything general, with no ad-hoc hard-coded hacks;
tactics tucked away in their own implementation package, not a top-level concept; the layering held
by a check whose list of exceptions only shrinks; the body's shape read from its spec (the stance
over any set of ends, the quadruped on the command layers) waits until a second body family needs
it, its imports kept on that list meanwhile.

**Decided here, which the owner may reverse**: the seam's name, `Decider`; the tactics package at
`src/core/mind/tactics/`, holding the fighter kind and its presets; the part framework at
`src/core/parts/`.

**What must not move**: every bout, Crypt run, fall and Lab scenario, bit for bit
(`scripts/fingerprint.mjs`); the gate (`npm test`) at each step.

## The shape

| Layer | Knows | Never knows |
|---|---|---|
| A body | its muscles, assist, hands, the body as read, its senses, its contact labels, after-physics | who drives it, or how |
| The command layers (a toolkit layer any mind may build on its body) | motor control, a view, being released and resumed | the skills, the decider, sub-minds |
| The skills (`skillSet`) | the command layers, navigation, an `Intent` in | the decider's memory, report or decision |
| A decider (`Decider`: tactics, Option Mind's chooser, a drill's script, a person's keys) | the skills' report and its own memory | anything of another decider |
| A mind | its decider, skills, command layers and any sub-minds, put together; its memory, report and who has the body, assembled by it | the host's world |

The part framework sits under all of them, over the spec: any layer's parts are made through it.
The registries that list each kind (`mind/kinds.ts`, `controllers.ts`, `lookup.ts`, `catalog.ts`,
`src/core/models.ts`'s default minds) are where the layers meet, and import every kind by design.

## Steps

Each lands green on its own: `npm run check`, `npm test`, `npm run build` where browser code moves;
each shortens the check's list of exceptions (step 1), and names by how much.

- **The fingerprint, a step at a time**: `node scripts/fingerprint.mjs --json` at the commit
  before, `--compare` at the step; the outcomes do not move. `--compare` reports a state reshaped
  without failing; nothing keeps a saved state across commits, so a state's shape may move.
- **A step's moves land in one commit**: a case's code identity is its modules' hashes and paths
  (`caseCoder`, `scripts/build-identity.mjs`), so each commit that moves files keys the saved
  evaluation rows anew and the next evaluation plays them again.
- **What a move also updates**: the build identity's role paths (`CUTS.roles`, `CUTS.store`), the
  boundary test's adapters (`MIND_ADAPTERS`), the fingerprint's own imports, and the
  architecture's sections the step makes wrong.
- **Commits**: a step that touches the toolkit and an entrant lands as two commits, the toolkit's
  first (`node scripts/entrant-check.mjs`), or as one named mixed where the toolkit's alone would
  not build.
- **Order with the [Commander plan](2026-10-29-commander.md)**: steps 2 and 3 land before it
  begins; the rest may land before or after.

### 1. The layer check

A rule in `tests/core-boundary.test.mjs`, beside `COMMAND_BARRED`: each module of `src/core/` has a
layer (`LAYERS`, by folder or by file, in the architecture's table order, the part framework's
among them), and an import (every one the mind rule reads, `ts.preProcessFile`, type-only ones
among them) names a module of its own layer or one below; the registries are exempt. Today's
up-stack imports are listed (`UP_STACK`), each `from -> to` with the step here that removes it, or
"a second body family" for the body's shape. The rule fails on an up-stack import not listed, on a
listed one the code no longer has (so the list is exact and only shrinks), and on a module with no
layer. A control case plants an import up the stack and sees it named. The architecture's layer
table gains the part framework's row and drops its note that the boundary test does not hold the
order.

Check: the gate, with the rule and its control; the list's length named in the commit.

### 2. The skills hold nothing of the layer above

- `skillSet`, `recipeSkills`, `combatSkills` and `fighterSkills` take no tactics argument; the
  skill set's state drops `tactics`, and `SkillReport` drops `engagement`.
- A mind assembles its own memory and report: `createFighter` (the fighter kind's, which Vanguard
  is), `driveFighter`, `createOptionMind` and the Lab's scripted drive return
  `state: { skills: skills.state, decider: decider.state }` and a `MindReport` whose `engagement`
  is the decider's (`skillsReport(skills, decider)`, `src/core/mind/minds.ts`, which exists);
  `driveBy` returns both. The drill opponent builds no skills of its own and is unchanged.
- Every reader of `skills.report.engagement` reads the mind's report instead
  (`MindMade.report.engagement`): the mind inspector (`src/ui/mind-inspector.ts`, the Arena's, the
  Crypt's and the Lab's), the Arena's readout and HUD (`src/arena/fighter-readout.ts`,
  `fighter-hud.ts`, `main.ts`), the drills' readers (`src/evaluation/strike/read.ts`,
  `gait/read.ts`, `cover/read.ts`), the Lab (`src/lab/attack-mode.ts`, `attack-scenario.ts`), the
  action readout (`src/ui/action-readout.ts`), the tests and fixtures that read it
  (`tests/tactics-contract.test.mjs`, `entrant-vanguard.test.mjs`, `lab-targets.test.mjs`,
  `tests/fixtures/swap/stub-tactics.mjs`) and the research scripts (`research/arena-combat.mjs`,
  `ground-combat.mjs`).
- The fork case already forks every mind kind's presets (`tests/mind-contract.test.mjs`, "forks and
  resumes"); it catches a memory that falls out of a mind's state, so no test is added.

Check: the gate; the fingerprint's outcomes unchanged.

### 3. A neutral seam, and the reports apart

- `Decider<S = Sight, I = Intent, D = unknown>` (`src/core/mind/decider.ts`): `name`,
  `decide(sight, dt)`, `state`, `engagement`, and `decision`, what the skills prepared for it read
  live (`D`; the tactics' `TacticalDecision`), so the skills read a decision through the seam and
  never a tactics type. `Sight` and `driveBy` with it. `MindWiring.script`, `Controller` and
  `Scripted` name `Decider`. `Tactics` is gone as a toolkit name.
- `src/core/mind/engagement.ts`: `Engagement`, `EngagementDetail`, `engagementWithDetails`, and the
  readout's own types of what a decider weighed (`Offer`, `OfferTerms`, and a candidate and its
  pending action, which `action-tactics.ts` then fills). No readout type names a decider's module.

Check: the gate; the fingerprint's outcomes unchanged.

### 4. The part framework in its own place

`src/core/parts/`: `parts.ts`, `fields.ts` and the lookup's contract (`PartLookup`), reaching
nothing above the spec (what `parts.ts` reads of `body.ts` moves with it or below it). Each role's
contract sits with its layer: the motor's in `control/` (as now), the executors' and the legs'
(`executor-part.ts`, `locomotion-part.ts`) in `skills/`, the tactics' with them in step 5; the
lookup itself (`lookup.ts`) and the catalog stay registries.

Check: the gate; the fingerprint's outcomes unchanged.

### 5. Tactics as a package

`src/core/mind/tactics/`, an implementation of `Decider`: `tactics-part.ts` (`TacticsPart`,
`tacticsOf`, `prepareTacticsSkills`), `planners.ts`, `action-tactics.ts`, `behaviours/`,
`behaviours.ts`, `behaviour-part.ts`, `stand-tactics.ts`, `script-tactics.ts`, `TacticalDecision`,
and the fighter kind built on them: `createFighter`, `driveFighter`, `FIGHTER_MIND`

- **What stays in the toolkit**, under names that say what it is: what a decider is made from
  (`TacticsMaking` as `DeciderMaking`, and `ActionEstimates`, which `action-config.ts` and
  `executor-part.ts` read); the body layer from a kit (`fighterSkills` as `kitSkills`), the body's
  options from a mind's parts (`fighterBody` as `kitBody`), `kitFaults`; the conditions
  (`conditions.ts`, `ConditionConfig`), which Move's rules read (`skills/move.ts`,
  `distance-rule.ts`, `standing-rule.ts`); `action-producer.ts` (the ground fight's,
  `ground/ground-fight.ts`), `ordered.ts` (Option Mind's following orders) and `targets.ts` (the

- Vanguard, the drill opponent's presets, the Lab's scripted drive, `src/core/tasks/support-entry.ts`

Check: the gate; the fingerprint's outcomes unchanged.

### 6. Each layer's config with its layer

`src/core/mind/config.ts` keeps the minds' configs that no package owns, and the registries' unions:

- the skills' (`ActionConfig`, `ExecutorEntry`) in `src/core/skills/configs.ts`, an action's aim a
  `PartConfig` (the union of aims, `AimConfig`, staying with its registry, `mind/aims.ts`); `MOVE`
  with its part (`skills/move-part.ts`); a gait names its legs as a `PartConfig`
  (`skills/gaits.ts`), the union of every legs kind (`LocomotionConfig`) staying with its registry
  (`mind/locomotions.ts`);
- `SkillKit` declared on its own fields (locomotion, navigation, guard, support, executors,
  actions, motor), not a `Pick` of `FighterConfig`; the field names are kept, as saved configs and
  mind links carry them;
- the tactics' (`FocusRuleConfig`, `SelectorConfig`, `BehaviourConfig`, `BehavioursConfig`,
  `TacticsConfig`, `FIGHTING`), `FighterConfig` and the fighter presets (`RECIPE_FIGHTER`,
  `CLASSIC`, `PUNCHER`, `COUNTER_PUNCHER`, `BEHAVIOURS`, `DUELLIST`) in the package
  (`tactics/config.ts`), which `src/core/models.ts` (a model's default mind) and the research tasks
  (`src/core/tasks/support-entry.ts`) import;
- the quadruped's (`QuadrupedConfig`, `QUADRUPED` and its parts' unions) in `src/core/reptile/`.

Check: the gate; the fingerprint's outcomes unchanged.

### 7. Scripts drive any mind by a decider

- Drills drive no mind by a decider: they give orders, by the [drills by orders plan](2026-10-30-drills-by-orders.md),
  which deletes the drill deciders and the controllers' drill hooks.
- The Lab's script (`Scripted`, `MindWiring.script`) takes a `Decider` and the mind's own config
  type, not `FighterConfig`. What a script asks of the skills it is driven over (`prepareSkills`)
  is the script role's own hook, reading the decision through the seam (step 3).
- The layer check lists the package as a layer of its own that only the minds built on it and the
  registries import, which replaces a rule of its own.

Check: the gate; the fingerprint's outcomes unchanged.

### 8. One way into a body; the command layers a toolkit layer

- **One way in**: a mind takes its body through the host once (`BodyHost.take`), as a `Mind` made
  from its `OwnBody`, which gains its senses, its contact labels (`contactIdentity`, a grant today
  passed through `host.ts` and `fighterBody`) and an after-physics hook (`afterPhysics`, today
  wired by hand inside `createBody`). The host builds the fight's `PhysicalBody` the same way for
  every mind; who has the body (`PhysicalBody.has`) is the mind's (`Mind.has`), the names it
  reports unchanged (`hosting`'s host reports `"command"`), and its readers ask the predicate
  (`commandsBody`, `body.ts`) rather than compare names (`src/lab/ground-mode.ts`,
  `src/ui/mind-inspector.ts`, `research/arena-combat.mjs`). `BodyHost.command`, `hosted` and
  `policy` go.
- **The command layers** (`commandLayers(own, options)`, `src/core/control/command-layers.ts`): a
  `HostMind` (look, act, release, resume) any mind builds on its own body, with motor control from
  the mind's motor part and a view; it returns the `Body` its drivers have. The policy mind
  (`createPolicyBody`, `mind/direct.ts`) is a `Mind` over `OwnBody` the same way, and its users
  (`src/core/tasks/posture-hold.ts`, `support-entry.ts`, `reach.ts`) build it so.
- **A body built outside a fight** (a test, a research script, a task) is built through the same
  way by one toolkit function, `commandedBody(built, world, options)`, which takes what
  `createBody` takes and returns what it returns: `tests/harness/` (`combat-combination.mjs`,
  `garbage.mjs`, `probes.mjs`), `tests/mind-contract.test.mjs`, `swap.test.mjs`,
  `scripts/fingerprint.mjs`, `src/evaluation/rising.ts`, `technique.ts`, `fall.ts`,
  `src/lab/actor.ts` and the research scripts change an import.
- **The order is kept**, body by body, so every step is the same to the bit: the body's
  after-physics listener registered after its mind is made, as now; the first look before the
  skills exist; Option Mind's ground executor's skill set made before its `driveBy`.

Check: the gate; the fingerprint's outcomes unchanged; in a browser, an Arena bout, a Crypt run and
the Lab's stand-up scenario look as they did.

### 9. Sub-minds out of the body

- `BodyOptions.subs` goes. A mind that hands its body over builds `hosting` (`mind/sub-mind.ts`)
  over its own command layers and its sub-minds: the fighter kind and Vanguard with `STAND_UP` and
  `lie`, and the harnesses that pass sub-minds (`src/evaluation/rising.ts`, `technique.ts`,
  `fall.ts`, `src/lab/actor.ts`, `lab-scenario.ts`, `ground-config.ts`, `ground-scenario.ts`,
  `main.ts`, `tests/fixtures/swap/mind.mjs`, the research harnesses that build a body with one).
- **The order is kept**: the command layers, then the sub-minds, made before the view's first
  look; the sub-minds' after-physics listeners (the ground fight's own skill set,
  `ground/ground-fight.ts`) registered before the skills'. The command layers' sub-mind flag
  (`subOwned`, which turns the ground reading on, `body.ts`) is their being released, as they know
  it, under the same rule.
- `SubMindMaker` (`mind/kit.ts`) takes what a mind hands it, the command layers' view among it,
  never the body module.

Check: the gate; the fingerprint's outcomes unchanged, the falls and stand-ups with it.

- `CONTACT_FRICTION` in a spec module the engine and control both read (`src/core/spec/`), since
  the engine's folder is barred to control (`MIND_BARRED`).

Check: the gate; the fingerprint's outcomes unchanged.

## Not here

- **The body's shape read from its spec**, until a second body family needs it: the skills' and
  motor control's segments read from the spec's effectors and ends, the stance over any set of
  ends rather than a pair of sides, one field for support ends (`BodySpec.ends` for the
  quadruped's `effectors[].support`), `commandRefusal` replaced by the parts' fits, and the
  quadruped's host replaced by the command layers. Its imports stay on the check's list, marked so.

## Done when

The layer check's list holds only the body's shape, each entry marked for a second body family;
the skills hold no decider's memory, report or decision; tactics are a package nothing but the
minds built on it and the registries import; the part framework sits under every layer; every
mind takes its body one way and builds what it uses over it; and every case plays as before, bit
for bit.
