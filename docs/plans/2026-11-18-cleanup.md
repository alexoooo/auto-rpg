# The cleanup: the poor code of 13 to 18 November taken out

**Ordered by the owner on 2026-11-18**, after an audit of everything added from `9685d3b2c^` to
`ffc71efcc` found 75 defects against [the code recipe](../recipes/code.md)'s first rule ("Clean,
simple and general"). It goes ahead of further feature work: Initiative's measurements in play
finish and are recorded in [its plan](2026-11-18-initiative.md); nothing new is built on
[the back step](2026-11-16-back-step.md) or Initiative until this lands. Items 1 to 53 and 69 are
done, each with its commits; the rest of step 3 is in hand, then step 4 and step 5.

## The goal, in the owner's words

On 2026-11-18, to the reviewing session, on seeing Initiative built as a field of the `Objective`
interface with its formula in the chooser: "we have interface Objective which is swappable, you
hard-coded initiative into it, but aggression is implemented in a clean and general way instead?"

like this?" And, of the first answer: "i didn't mean just exactly this bad code pattern, i mean
what other bad code was introduced? the most important thing is to maintain and even increase the
code quality of this project. we need to implement everything in the most simple and general way
that we can. we spent a lot of effort to try to clean up this code, and it looks like you're
intorducing a lot of bad code again." Of the code the audit found kept for older saved data: "this
is an in-development vibe-coded game, 'backwards compatibility' is not a thing. please write teh
cleanup plan."

Of the testbed (2026-11-17, [its rest](2026-11-18-testbed-rest.md)), which bears on step 3: "making
the 'profiles' a pluggable contract that can have multiple implementations" and "a general ai
testbed, that we can experiment on without being locked in to one way of doing things".

## What done is

1. **Every item below is fixed**, or shown to be no defect with the reason written beside it here.
   A fix that adds a flag, a cast, an optional parameter or a second copy is not a fix.
2. **Nothing the game computes moves**, but for the items marked **moves**: the fingerprint
   (`node scripts/fingerprint.mjs`) is read before and after each commit and is identical.
3. **The gate holds at each commit**: `npm run check`, `npm test`, `npm run build`.
4. **What the audit did not read is read** (step 5), and what it finds is fixed the same way.
5. **The rules that would have stopped this are in the code recipe** (the last section).

## The order

Deletions first, then what is written twice, then the reshaping, then comments and tests, then the
unread. Within a step the order is the worker's. One commit an item, or a few items of one file,
naming the item numbers. **Done in** names the commits that fixed an item; an item without it is
open. Each item is an audit reader's report, confirmed against the code as it is fixed. Line
numbers are of `ffc71efcc`.

## What goes into the code recipe when this lands

- An experiment is a kind behind its contract, selected by a config, or it is deleted when its
  reading is in; never a flag, a string or an optional parameter in the code every kind shares.
- A stored file has one shape. When the shape changes, the file is rewritten or made again in the
  same commit; no reader allows for the old one.
- A new need is not a new trailing parameter: past three positionals, or at the first boolean, a
  function takes named fields.
