# Mind data: packed per kind

## Why

Mind data loads per use ([architecture](../architecture.md#minds)), so a page fetches only the
data its minds read. What is left is size: the five files are about 28 MB of JSON, and every
action that carries data adds to it. A get-up's motion kept at 30 Hz is tens of KB and a network
about 0.2 MB, so stored as small integers 100 actions are some megabytes on the server and a bout
downloads only the handful it fields.

Data ships as compressed binary arrays, each in the encoding its kind can bear, decoded into the
plain values the minds read now: lossless first (step 2), then a precision measured per kind
(step 3), when the next action that carries data arrives. Step 4 waits on the owner: Research
rise's response tables.

The owner has decided: brotli is acceptable, and no algorithm or representation is fixed;
recomputing on the device to save transfer is a good trade; precision is chosen per kind of data
(a network's weights may be smaller than a motion's angles); art textures are out of scope.

## Where it starts

Steps 0 and 1 have landed. Each key's data is a module of its own in `src/core/data/`, imported
only by `loadData` (`src/core/data/store.ts`); a part says what it reads (`Part.reads`) and
`treeData` (`src/core/mind/catalog.ts`) collects a tree's; Node loads every key through
`tests/harness/preload-data.mjs`. The fingerprint has a case for each part that reads mind data
(`DATA_CASES`, `scripts/fingerprint.mjs`), the reference for steps 2 and 3. Each of the four keys
is a chunk of its own in the production build:

| File | What it is | Size | Who reads it |
|---|---|---|---|
| `assets/research/research-rise.json` | Research rise: three recorded get-ups, a club get-up, 104 measured response tables | 19.3 MB | The `research-rise` sub-mind (`src/core/mind/rise/research-part.ts`) |
| `assets/research/research-rise-unshod-warrior.json` | Research rise: two more get-ups for the empty-handed Warrior without soles | 3.2 MB | The same |
| `assets/core/learned-rise.json` | A ReLU network, 99-256-256-15, 95,247 numbers | 2.0 MB | A `stand-up` whose `techniques` list `learned-rise` (`src/core/mind/ground/learned-rise.ts`) |
| `assets/core/learned-run.json` | A ReLU network, 47-256-256-12, 81,164 numbers | 1.7 MB | The `learned-run` locomotion, when its `policy` is not null (`src/core/skills/learned-run-part.ts`) |
| `assets/core/learned-punch.json` | A ReLU network, 55-256-256-18, and each body's punch settings; 84,855 numbers | 1.8 MB | The learned punch, when an executor's `learned` is set (`src/core/skills/learned-punch.ts`) |

Research rise's three recorded get-ups (227,500 numbers), measured in Node on the bundled JSON with
`node:zlib` at maximum settings:

| Encoding | Raw | gzip | brotli |
|---|---|---|---|
| JSON text | 3,451 KB | 1,509 KB | 1,273 KB |
| 32-bit floats | 889 KB | 625 KB | 586 KB |
| 32-bit floats, byte planes | 889 KB | 519 KB | 497 KB |
| 16-bit, steps of 0.001 | 444 KB | 250 KB | 195 KB |
| 16-bit, steps of 0.001, change from the previous frame | 444 KB | 187 KB | 156 KB |

- The first get-up's angles kept every 4th frame (30 Hz) and interpolated linearly are off by 0.06
  degrees on average and 5.7 degrees at worst (around contacts).
- The 104 response tables do not compress by structure: twenty principal components leave 43 % of
  them unexplained.
- Storing 64-bit floats exactly saves almost nothing over brotli'd JSON (6.7 MB for Research rise),
  so a real gain needs a lower precision.

## Design: the packed file

```
"ARPD"  u8 version (1)  u8 compression (0 none, 1 gzip, 2 brotli)  then, compressed:
  u32 header length, LE | header (UTF-8 JSON) | zero padding to 8 | blocks
header = { "tree": <the data, each packed part replaced by { "$": index }>,
           "blocks": [{ "encoding": ..., "length": n, "offset": bytes, ... }] }
```

| Packed part | What it holds |
|---|---|
| Array | a homogeneous array of numbers, with `shape` for a matrix (a network's `weights`) |
| Table | an array of objects (a motion's frames) as columns, one per key path (`angles.0` to `angles.34`, `loads.head`, `handPoses.left`). A key a row lacks is a column's absent mark, so frames whose kinds carry different keys (`muscles`, `host`) keep them. A column is encoded on its own, optionally as a delta along the rows; the decoder rebuilds objects with the source's key order. This holds 23,788 small arrays in a few hundred columns and makes change-from-the-previous-frame expressible. |
| Exceptions | a numeric column's non-number values as `(row, value)` pairs. Research rise's frame `velocity` mixes numbers with `"+inf"` and `"-inf"` (`src/core/mind/rise/reference-types.ts`), and `src/core/mind/rise/reference-path.ts` branches on `typeof v === "number"`, so they are restored as strings, never `Infinity`. |

| Encoding | Bytes a value | Decoded value |
|---|---|---|
| `f64` | 8 | exactly the stored double |
| `f32` | 4 | the float widened, exactly |
| `i16` `{ step, delta? }` | 2 | `q * step`; with `delta`, `q` is the running sum of the stored integers |
| `i8` `{ scales }` | 1 | `q * scales[row]`, one scale per row of a matrix |
| `u8` `{ labels }` | 1 | `labels[q]`, for strings such as a hand's pose or a frame's `kind` |

Decoding uses `*` and `+` only, so every JavaScript engine decodes the same doubles (`EXACT_MATH`),
and returns plain arrays and objects, so the minds read what they read now.

## Steps

Each is a toolkit change, read with the fingerprint against the commit before it, `DATA_CASES`
included.

### 2. The packed format, lossless

The format and its loaders land with exact encodings only, so no bout moves.

- `src/core/data/packed.ts`: `unpack(bytes: Uint8Array): unknown`, pure, over decompressed bytes.
- `scripts/pack-data.mjs <key>` reads the key's source JSON and writes `public/data/<key>.arpd`: a
  table for an array of objects, an array for an array of numbers, per-column encodings from a
  table in the script (`f64` and labels throughout in this step). The networks' `*.meta.json`
  files, which the skills and the editor read synchronously, stay as they are.
- The source JSON stays in the repository as the packer's input; `scripts/bundle-research-rise.mjs`
  keeps writing it, and no module imports it, so it stays out of the bundle.
- The loaders read `public/data/<key>.arpd` through a reader the host gives, `loadData(keys, read)`
  with `read: (file: string) => Promise<Uint8Array>` returning decompressed bytes: in the browser
  `src/data-read.ts` (`fetch(publicAssetUrl("/data/" + file))`, `DecompressionStream`); in Node
  `tests/harness/preload-data.mjs` (`readFile`, `node:zlib`). The core calls neither `fetch` nor
  `DecompressionStream`.
- **A case's code keeps its data**: a key's code (`caseCoder`, `scripts/build-identity.mjs`) is
  today its store module's import closure, which holds the JSON. Once the bytes are fetched, it
  also holds `public/data/<key>.arpd`, so re-encoding a file (step 3) keys its cases anew.
- The extension is `.arpd`, not `.br`, so no server applies `Content-Encoding` and the browser
  always receives the compressed bytes; `.gitattributes` gets `*.arpd binary` (`core.autocrlf` is
  on in this clone).
- `AGENTS.md`'s "The core reaches only itself" says mind data is read through
  `src/core/data/store.ts`, from bytes its host supplies; the architecture's mind data paragraph
  says how the files are packed and read.
- **The compression byte**: check `new DecompressionStream("brotli")` in current Chrome, Firefox and
  Safari. If every one has it, brotli; otherwise gzip (supported
  everywhere), or brotli with a decoder shipped beside the store if its size (tens of KB) is worth
  the difference (about 15 % at these sizes). The header's byte keeps the choice per file.

Check, once, with a scratch script: each encoding and the table round-trip through the packer's
writer and `unpack`, to the bit for `f64`, `f32` and labels, within half a step for `i16` and `i8`;
a truncated file and an unknown version are refused by name; each file in `public/data/` decodes
to exactly its source JSON (every number by `Object.is`, every string and key order equal), which
for a lossless file proves no bout moves whatever the fingerprint covers (step 3 narrows it to the
columns it leaves exact). The fingerprint names no moved case; a `.arpd` file's edit changes the
code of the cases whose minds read it, and of no other; after `npm run build`, no chunk holds a
source JSON.

### 3. Precision per kind, measured

One commit a file, naming the encoding, the bytes before and after, the measurement below read
before and after on the same machine, and the fingerprint's moved cases (`DATA_CASES`).

| Data | Encoding to try first | Measurement |
|---|---|---|
| `learned-rise` network | `i8` per row (4x under `f32`); `i16` if it loses | the largest change of the network's output over the features a Lab Stand-up round records; the owner's 64-fall target, `node research/rising-bed.mjs --target --techniques learned-rise` |
| `learned-run` network | the same | the output change over a recorded run's features; a short run on the Warrior and the Rogue in the Lab's locomotion scenario, its distance and falls |
| `learned-punch` network | the same | the output change over a drill's recorded features; the learned punch's Strike drill subject, and the fingerprint's `data: learned-punch` case |
| Research rise get-ups | `i16`, `delta`, step 0.001 for angles; a step per column (speeds, velocities, loads) from its range | the owner's 64-fall target, `node research/rising-bed.mjs --target --sub research-rise`, its `--sub` (now `support-recovery` or `stand-up`) first gaining `research-rise`, a research change of its own |
| Hand poses, frame `kind` | `u8` labels | exact |

Check: a file whose measurement drops beyond the run-to-run spread gets more bits.

### 4. Research rise's response tables (waits)

Only when the owner asks. 12.5 MB of it is its first get-up's response
tables: 104 samples, each a `columns` and a `coastColumns` matrix, 35 by 80, measurements of the
body's own physics. The script that measured them is not in the repository
(`scripts/bundle-research-rise.mjs` packages gzipped references made elsewhere), so recomputing
them on the device is not yet easy.

1. Measure Research rise with its first get-up as a `path` controller like the other two (no
   responses), on step 3's Research rise measurement, the owner's 64-fall target.
2. If it holds, drop the response tables: Research rise falls to a few hundred KB.
3. If not, recompute on the device. First recover from `responsePolicy`
   (`src/core/mind/rise/reference-response.ts`) and the references' history what `columns` and
   `coastColumns` each measure: the response to a nudge of each of the 35 muscle speed requests,
   read as the change of the 80 features `responseFeatures` reads, and the response coasting after
   it. Then at each sampled step fork the world (`saveState`/`loadState`, `world.physics.save()`),
   nudge each request in turn, and read both matrices. Time it; if it is too slow at a bout's
   start, compute it once per device and keep it in IndexedDB, keyed by the
   build's identity.

Check: the fingerprint's moved cases are named in the commit.

## Checks

- Every step: `npm run check` and `npm test`, with `npm run build` where browser code changes.
- Step 2 changes no bout: the fingerprint names no moved case, and its decoded data equals its
  source to the bit. Steps 3 and 4 move the cases of the data they touch, and their commits name
  them.
- Construction stays synchronous: `new Duel`, `enlist`, `createMind`, `createBody`'s sub-minds and
  the Dungeon's mid-run `wake()` (inside a world step) cannot await, so data is loaded before.
- A mind built without its data still fails when built, naming the key and how to load it; it
  never runs with a substitute and never fails later, mid-bout.
- Every check runs in minutes; none is a battery read for its own sake.

## Done when

Data ships packed at a precision measured per kind (steps 2 and 3), and a case's code holds the
packed files its minds read. Afterwards, a CI check of the built bundle
(`.github/workflows/pages.yml`, after `npm run build`) holds the arena's startup chunks under a set
size, and new actions with data join through the store and the packer from the start.
