# Mind data: packed per kind

## Why

Mind data loads per use ([architecture](../architecture.md#minds)), so a page fetches only the
data its minds read. What is left is size: every action that carries data adds to it. A motion kept
at 30 Hz is tens of KB and a network about 0.2 MB, so stored as small integers 100 actions are some
megabytes on the server and a bout downloads only the handful it fields.

Data ships as compressed binary arrays, each in the encoding its kind can bear, decoded into the
plain values the minds read now: lossless first (step 2), then a precision measured per kind
(step 3).

The owner has decided: brotli is acceptable, and no algorithm or representation is fixed;
recomputing on the device to save transfer is a good trade; precision is chosen per kind of data
(a network's weights may be smaller than a motion's angles); art textures are out of scope.

## Where it starts

Each key's data is a module of its own in `src/core/data/`, imported
only by `loadData` (`src/core/data/store.ts`); a part says what it reads (`Part.reads`) and
`treeData` (`src/core/mind/catalog.ts`) collects a tree's; Node loads every key through
`tests/harness/preload-data.mjs`. The fingerprint has a case for each part that reads mind data
(`DATA_CASES`, `scripts/fingerprint.mjs`), the reference for steps 2 and 3. Each key is a chunk of
its own in the production build:

| File | What it is | Size | Who reads it |
|---|---|---|---|
| `assets/core/learned-punch.json` | A ReLU network, 55-256-256-18, and the Warrior's punch settings (the only body it has); 84,855 numbers | 1.8 MB | The learned punch, when an executor's `learned` is set (`src/core/skills/learned-punch.ts`) |

Measured on Research rise's three recorded get-ups (227,500 numbers,
`assets/research/research-rise.json@20ea40e6`), in Node with `node:zlib` at maximum settings:

| Encoding | Raw | gzip | brotli |
|---|---|---|---|
| JSON text | 3,451 KB | 1,509 KB | 1,273 KB |
| 32-bit floats | 889 KB | 625 KB | 586 KB |
| 32-bit floats, byte planes | 889 KB | 519 KB | 497 KB |
| 16-bit, steps of 0.001 | 444 KB | 250 KB | 195 KB |
| 16-bit, steps of 0.001, change from the previous frame | 444 KB | 187 KB | 156 KB |

- A get-up's angles kept every 4th frame (30 Hz) and interpolated linearly are off by 0.06 degrees
  on average and 5.7 degrees at worst (around contacts).
- Storing 64-bit floats exactly saves almost nothing over brotli'd JSON, so a real gain needs a
  lower precision.

## Design: the packed file

```
"ARPD"  u8 version (1)  u8 compression (0 none, 1 gzip, 2 brotli)  then, compressed:
  u32 header length, LE | header (UTF-8 JSON) | zero padding to 8 | blocks
header = { "tree": <the data, each packed part replaced by { "$": index }>,
           "blocks": [{ "encoding": ..., "length": n, "offset": bytes, ... }] }
```

| Packed part | What it holds |
|---|---|
| Array | a homogeneous array of numbers, with `shape` for a matrix (a network's `weights`) |
| Table | an array of objects (a motion's frames) as columns, one per key path (`angles.0`, `loads.head`, `handPoses.left`). A key a row lacks is a column's absent mark, so frames whose kinds carry different keys keep them. A column is encoded on its own, optionally as a delta along the rows; the decoder rebuilds objects with the source's key order. |
| Exceptions | a numeric column's non-number values as `(row, value)` pairs, restored as they were stored (a string stays a string, never `Infinity`) |

| Encoding | Bytes a value | Decoded value |
|---|---|---|
| `f64` | 8 | exactly the stored double |
| `f32` | 4 | the float widened, exactly |
| `i16` `{ step, delta? }` | 2 | `q * step`; with `delta`, `q` is the running sum of the stored integers |
| `i8` `{ scales }` | 1 | `q * scales[row]`, one scale per row of a matrix |
| `u8` `{ labels }` | 1 | `labels[q]`, for strings such as a hand's pose or a frame's `kind` |

Decoding uses `*` and `+` only, so every JavaScript engine decodes the same doubles (`EXACT_MATH`),
and returns plain arrays and objects, so the minds read what they read now.

## Steps

Each is a toolkit change, read with the fingerprint against the commit before it, `DATA_CASES`
included.

### 2. The packed format, lossless

The format and its loaders land with exact encodings only, so no bout moves.

- `src/core/data/packed.ts`: `unpack(bytes: Uint8Array): unknown`, pure, over decompressed bytes.
- `scripts/pack-data.mjs <key>` reads the key's source JSON and writes `public/data/<key>.arpd`: a
  table for an array of objects, an array for an array of numbers, per-column encodings from a
  table in the script (`f64` and labels throughout in this step). A network's `*.meta.json` file,
  which the skills and the editor read synchronously, stays as it is.
- The source JSON stays in the repository as the packer's input, and no module imports it, so it
  stays out of the bundle.
- The loaders read `public/data/<key>.arpd` through a reader the host gives, `loadData(keys, read)`
  with `read: (file: string) => Promise<Uint8Array>` returning decompressed bytes: in the browser
  `src/data-read.ts` (`fetch(publicAssetUrl("/data/" + file))`, `DecompressionStream`); in Node
  `tests/harness/preload-data.mjs` (`readFile`, `node:zlib`). The core calls neither `fetch` nor
  `DecompressionStream`.
- **A case's code keeps its data**: a key's code (`caseCoder`, `scripts/build-identity.mjs`) is
  today its store module's import closure, which holds the JSON. Once the bytes are fetched, it
  also holds `public/data/<key>.arpd`, so re-encoding a file (step 3) keys its cases anew.
- The extension is `.arpd`, not `.br`, so no server applies `Content-Encoding` and the browser
  always receives the compressed bytes; `.gitattributes` gets `*.arpd binary` (`core.autocrlf` is
  on in this clone).
- `AGENTS.md`'s "The core reaches only itself" says mind data is read through
  `src/core/data/store.ts`, from bytes its host supplies; the architecture's mind data paragraph
  says how the files are packed and read.
- **The compression byte**: check `new DecompressionStream("brotli")` in current Chrome, Firefox and
  Safari. If every one has it, brotli; otherwise gzip (supported everywhere), or brotli with a
  decoder shipped beside the store if its size (tens of KB) is worth the difference (about 15 % at
  these sizes). The header's byte keeps the choice per file.

Check, once, with a scratch script: each encoding and the table round-trip through the packer's
writer and `unpack`, to the bit for `f64`, `f32` and labels, within half a step for `i16` and `i8`;
a truncated file and an unknown version are refused by name; each file in `public/data/` decodes
to exactly its source JSON (every number by `Object.is`, every string and key order equal), which
for a lossless file proves no bout moves whatever the fingerprint covers. The fingerprint names no
moved case; a `.arpd` file's edit changes the code of the cases whose minds read it, and of no
other; after `npm run build`, no chunk holds a source JSON.

### 3. Precision per kind, measured

One commit a file, naming the encoding, the bytes before and after, the measurement below read
before and after on the same machine, and the fingerprint's moved cases (`DATA_CASES`).

| Data | Encoding to try first | Measurement |
|---|---|---|
| `learned-punch` network | `i8` per row (4x under `f32`); `i16` if it loses | the output change over a drill's recorded features; the held-out check (`research/punch-policy-check.mjs`), and the learned puncher's Strike drill (`research/learned-puncher.json`), and the fingerprint's `data: learned-punch` case |
| A motion's frames (when an action with one comes) | `i16`, `delta`, step 0.001 for angles; a step per column from its range | its skill's drill |
| Hand poses, frame `kind` | `u8` labels | exact |

Check: a file whose measurement drops beyond the run-to-run spread gets more bits.

## Checks

- Every step: `npm run check` and `npm test`, with `npm run build` where browser code changes.
- Step 2 changes no bout: the fingerprint names no moved case, and its decoded data equals its
  source to the bit. Step 3 moves the cases of the data it touches, and its commits name them.
- Construction stays synchronous: `new Duel`, `enlist`, `createMind`, `createBody`'s sub-minds and
  the Dungeon's mid-run `wake()` (inside a world step) cannot await, so data is loaded before.
- A mind built without its data still fails when built, naming the key and how to load it; it
  never runs with a substitute and never fails later, mid-bout.
- Every check runs in minutes; none is a battery read for its own sake.

## Done when

Data ships packed at a precision measured per kind (steps 2 and 3), and a case's code holds the
packed files its minds read. Afterwards, a CI check of the built bundle
(`.github/workflows/pages.yml`, after `npm run build`) holds the arena's startup chunks under a set
size, and new actions with data join through the store and the packer from the start.

## Relations

- A browser worker that plays cases (a live run on the Ratings screen,
