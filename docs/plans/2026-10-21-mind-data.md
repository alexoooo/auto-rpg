# Mind data: loaded per use, packed per kind

## Why

The game is to be playable on a phone, with 100 or more actions, yet every page that opens the
arena, the crypt or the lab downloads every mind's data, used or not. A get-up's motion kept at
30 Hz is tens of KB and a network about 0.2 MB, so with data loaded per use and stored as small
integers, 100 actions are some megabytes on the server and the handful a bout fields on the phone.

Two changes, in order: **per use** (steps 0 and 1, now), where a screen loads the data its minds
need before it builds them, under its loading overlay, and nothing a bout does changes; then
**packed** (steps 2 and 3, when the next action that carries data arrives, or a phone build fields
a mind that reads data), where data ships as compressed binary arrays, each in the encoding its kind
can bear, decoded into the plain values the minds read now. Step 4 waits: once loading is per use,
Research rise's tables download only for a player who picks that experimental part.

The owner has decided: brotli is acceptable, and no algorithm or representation is fixed;
recomputing on the device to save transfer is a good trade; precision is chosen per kind of data
(a network's weights may be smaller than a motion's angles); art textures are out of scope.

## Where it starts

The production build's `models-*.js` chunk is 26.4 MB (11 MB gzipped), about 25 MB of it four JSON
files:

| File | What it is | Size | Who uses it |
|---|---|---|---|
| `assets/research/research-rise.json` | Research rise: three recorded get-ups, a club get-up, 104 measured response tables | 19.3 MB | Only a mind that lists the `research-rise` sub-mind |
| `assets/research/research-rise-unshod-warrior.json` | Research rise: two more get-ups for the empty-handed Warrior without soles | 3.2 MB | The same |
| `assets/core/learned-rise.json` | A ReLU network, 99-256-256-15, 95,247 numbers | 2.0 MB | Built by every Warrior and Rogue `stand-up`; run only if `learned-rise` is listed |
| `assets/core/learned-run.json` | A ReLU network, 47-256-256-12, 81,164 numbers | 1.7 MB | Only the `learned-run` locomotion |

Research rise's three recorded get-ups (227,500 numbers), measured in Node on the bundled JSON with
`node:zlib` at maximum settings:

| Encoding | Raw | gzip | brotli |
|---|---|---|---|
| JSON text | 3,451 KB | 1,509 KB | 1,273 KB |
| 32-bit floats | 889 KB | 625 KB | 586 KB |
| 32-bit floats, byte planes | 889 KB | 519 KB | 497 KB |
| 16-bit, steps of 0.001 | 444 KB | 250 KB | 195 KB |
| 16-bit, steps of 0.001, change from the previous frame | 444 KB | 187 KB | 156 KB |

- The first get-up's angles kept every 4th frame (30 Hz) and interpolated linearly are off by 0.06
  degrees on average and 5.7 degrees at worst (around contacts).
- The 104 response tables do not compress by structure: twenty principal components leave 43 % of
  them unexplained.
- Storing 64-bit floats exactly saves almost nothing over brotli'd JSON (6.7 MB for Research rise),
  so a real gain needs a lower precision.

## Design

### The store: `src/core/data/store.ts`

Outside the mind folders, so it may load; inside the core, so minds may read it. The loaded map is
a cache of frozen data, not a bout's state.

```ts
/** **Mind data**, by key: loaded before the minds that read it are built, and read synchronously after. */
export type DataKey = "learned-rise" | "learned-run" | "research-rise";

interface DataOf {
  "learned-rise": LearnedRiseData;
  "learned-run": LearnedRunData;
  "research-rise": ResearchRiseData;
}

const LOADERS: { readonly [K in DataKey]: () => Promise<DataOf[K]> } = {
  "learned-rise": () => import("../../../assets/core/learned-rise.json", { with: { type: "json" } }).then(m => deepFreeze(m.default)),
  "learned-run": () => import("../../../assets/core/learned-run.json", { with: { type: "json" } }).then(m => deepFreeze(m.default)),
  "research-rise": researchRiseData,
};

export const DATA_KEYS = Object.freeze(Object.keys(LOADERS) as DataKey[]);

/** Load `keys`; a key loads once a realm, and a failed load can be asked again. */
export function loadData(keys: Iterable<DataKey>): Promise<void>;

/** `key`'s data; throws, naming `loadData` and `tests/harness/preload-data.mjs`, when it is not loaded. */
export function dataOf<K extends DataKey>(key: K): DataOf[K];
```

- `researchRiseData` is in `src/core/data/research-rise.ts`, not `research.ts`, so there is no
  import cycle. It imports both research files dynamically, parses each `payload`, deep-freezes,
  and merges the unshod Warrior's entry as `research.ts`'s top level does (`bundle`, `additions`,
  `unshodWarrior`); `research.ts` keeps no top-level parse.
- Vite splits each dynamically imported JSON into a chunk of its own; Node imports JSON natively.
  `tests/core-boundary.test.mjs` walks literal dynamic imports (`ts.preProcessFile(..., true,
  true)`) and admits JSON under `assets/` (`isData`), so the boundary needs no change; tsc
  (`module: ESNext`, `moduleResolution: bundler`) accepts the import attributes.

### What a config needs: `treeData`

```ts
/** The data `config`'s parts read, every key once. */
export function treeData(config: PartConfig): readonly DataKey[];
```

Each part says what it reads, beside `faults`, and the catalog walks the tree as `treeFaults` does
(`src/core/mind/catalog.ts`):

| Part | Reads |
|---|---|
| sub-mind `research-rise` (`SUB_MIND_PARTS`, `src/core/mind/sub-minds.ts`) | `research-rise` |
| sub-mind `stand-up` | `learned-rise` when its `techniques` list `learned-rise` |
| skill `learned-run` (`SKILL_PARTS`, `src/core/mind/fighter.ts`) | `learned-run` when `policy` is not null |

### The packed file

```
"ARPD"  u8 version (1)  u8 compression (0 none, 1 gzip, 2 brotli)  then, compressed:
  u32 header length, LE | header (UTF-8 JSON) | zero padding to 8 | blocks
header = { "tree": <the data, each packed part replaced by { "$": index }>,
           "blocks": [{ "encoding": ..., "length": n, "offset": bytes, ... }] }
```

| Packed part | What it holds |
|---|---|
| Array | a homogeneous array of numbers, with `shape` for a matrix (a network's `weights`) |
| Table | an array of objects (a motion's frames) as columns, one per key path (`angles.0` to `angles.34`, `loads.head`, `handPoses.left`). A key a row lacks is a column's absent mark, so frames whose kinds carry different keys (`muscles`, `host`) keep them. A column is encoded on its own, optionally as a delta along the rows; the decoder rebuilds objects with the source's key order. This holds 23,788 small arrays in a few hundred columns and makes change-from-the-previous-frame expressible. |
| Exceptions | a numeric column's non-number values as `(row, value)` pairs. Research rise's frame `velocity` mixes numbers with `"+inf"` and `"-inf"` (`reference-types.ts`), and `reference-path.ts` branches on `typeof v === "number"`, so they are restored as strings, never `Infinity`. |

| Encoding | Bytes a value | Decoded value |
|---|---|---|
| `f64` | 8 | exactly the stored double |
| `f32` | 4 | the float widened, exactly |
| `i16` `{ step, delta? }` | 2 | `q * step`; with `delta`, `q` is the running sum of the stored integers |
| `i8` `{ scales }` | 1 | `q * scales[row]`, one scale per row of a matrix |
| `u8` `{ labels }` | 1 | `labels[q]`, for strings such as a hand's pose or a frame's `kind` |

Decoding uses `*` and `+` only, so every JavaScript engine decodes the same doubles (`EXACT_MATH`),
and returns plain arrays and objects, so the minds read what they read now.

## Steps

Each is a toolkit change on its own branch, read against main with the fingerprint and step 0's
cases. Before step 2, time the same Arena bout's steps (`__arena.world.step()` in a loop, through
remote debugging) in the owner's phone's browser and the desktop's, and a Crypt hall the same way,
naming device, engine and rate. It takes minutes and says which constraint binds: if the step is,
that is the next work, ahead of packing, and `research/step-time.mjs` says where the step goes.

### 0. Fingerprint cases for the data-reading minds

`scripts/fingerprint.mjs`'s cases (the `MINDS` presets, the stands, the crypt, the lab) list none of
`research-rise`, `learned-rise` or `learned-run`. Add three arena cases, the Warrior against the
Warrior on the open level, one side's mind changed:

| Case | The changed side's mind |
|---|---|
| `data: research-rise` | `CLASSIC` with `subs: [{ kind: "research-rise" }]` |
| `data: learned-rise` | `CLASSIC` with `subs: [{ ...STAND_UP, techniques: ["learned-rise"] }]` |
| `data: learned-run` | `CLASSIC` with its locomotion `learned-run`, policy `all-bodies` |

A bout in which the side is never down exercises no rise, so each case's record names how long the
side spent down, and its recipe (the opposing preset, the cap) is chosen so the side is down in its
first run.

Check: record `node scripts/fingerprint.mjs --only "^data:" --json` on main as the reference for
steps 1 to 3. A toolkit commit of its own.

### 2. The packed format, lossless

The format and its loaders land with exact encodings only, so no bout moves.

- `src/core/data/packed.ts`: `unpack(bytes: Uint8Array): unknown`, pure, over decompressed bytes.
- `scripts/pack-data.mjs <key>` reads the key's source JSON and writes `public/data/<key>.arpd`: a
  table for an array of objects, an array for an array of numbers, per-column encodings from a
  table in the script (`f64` and labels throughout in this step). It also writes
  `assets/core/learned-run.meta.json`.
- The source JSON stays in the repository as the packer's input; `scripts/bundle-research-rise.mjs`
  keeps writing it, `tests/core-research-rise.test.mjs` imports both research files directly, and
  `tests/data-budget.test.mjs` keeps them out of the bundle.
- The loaders read `public/data/<key>.arpd` through a reader the host gives, `loadData(keys, read)`
  with `read: (file: string) => Promise<Uint8Array>` returning decompressed bytes: in the browser
  `src/data-read.ts` (`fetch(publicAssetUrl("/data/" + file))`, `DecompressionStream`); in Node
  `tests/harness/preload-data.mjs` (`readFile`, `node:zlib`). The core calls neither `fetch` nor
  `DecompressionStream`.
- The extension is `.arpd`, not `.br`, so no server applies `Content-Encoding` and the browser
  always receives the compressed bytes; `.gitattributes` gets `*.arpd binary` (`core.autocrlf` is
  on in this clone).
- `AGENTS.md`'s "The core reaches only itself" says mind data is read through
  `src/core/data/store.ts`, from bytes its host supplies.
- **The compression byte**: check `new DecompressionStream("brotli")` in current Chrome, Firefox and
  Safari, the owner's phone among them. If every target has it, brotli; otherwise gzip (supported
  everywhere), or brotli with a decoder shipped beside the store if its size (tens of KB) is worth
  the difference (about 15 % at these sizes). The header's byte keeps the choice per file.

Check: `tests/core-packed.test.mjs` (fast): each encoding and the table round-trip through the
packer's writer and `unpack`, to the bit for `f64`, `f32` and labels, within half a step for `i16`
and `i8`; a truncated file and an unknown version are refused by name; each file in `public/data/`
decodes to exactly its source JSON (every number by `Object.is`, every string and key order equal),
which for a lossless file proves no bout moves whatever the fingerprint covers (step 3 narrows it to
the columns it leaves exact). The fingerprint, with step 0's cases, names no moved case.

### 3. Precision per kind, measured

One commit a file, naming the encoding, the bytes before and after, the measurement below read
before and after on the same machine, and the fingerprint's moved cases (step 0's).

| Data | Encoding to try first | Measurement |
|---|---|---|
| `learned-rise` network | `i8` per row (4x under `f32`); `i16` if it loses | the largest change of the network's output over the features a Lab Stand-up round records; `node --test tests/lab-stand-up-capability.test.mjs` with `learned-rise` |
| `learned-run` network | the same | the output change over a recorded run's features; no capability test configures it, so a short run on the Warrior and the Rogue in the Lab's locomotion scenario, its distance and falls |
| Research rise get-ups | `i16`, `delta`, step 0.001 for angles; a step per column (speeds, velocities, loads) from its range | `node --test tests/lab-research-rise-capability.test.mjs tests/lab-research-rise.test.mjs tests/core-research-rise.test.mjs` (the last includes the restored fall it reproduces) |
| Hand poses, frame `kind` | `u8` labels | exact |

### 4. Research rise's response tables (waits)

Only when Research rise is to be fielded on a phone. 12.5 MB of it is its first get-up's response
tables: 104 samples, each a `columns` and a `coastColumns` matrix, 35 by 80, measurements of the
body's own physics. The script that measured them is not in the repository
(`bundle-research-rise.mjs` packages gzipped references made elsewhere), so recomputing them on the
device is not yet easy.

1. Measure Research rise with its first get-up as a `path` controller like the other two (no
   responses), on step 3's three Research rise tests. To read it on the owner's 64-fall target too,
   `research/rising-bed.mjs`'s `--sub` (now `support-recovery` or `stand-up`) first gains
   `research-rise`, a research change of its own.
2. If it holds, drop the response tables: Research rise falls to a few hundred KB.
3. If not, recompute on the device. First recover from `responsePolicy`
   (`src/core/mind/rise/reference-response.ts`) and the references' history what `columns` and
   `coastColumns` each measure: the response to a nudge of each of the 35 muscle speed requests,
   read as the change of the 80 features `responseFeatures` reads, and the response coasting after
   it. Then at each sampled step fork the world (`saveState`/`loadState`, `world.physics.save()`),
   nudge each request in turn, and read both matrices. Time it on a phone-class CPU; if it is too
   slow at a bout's start, compute it once per device and keep it in IndexedDB, keyed by the
   build's identity.

Check: the fingerprint's moved cases are named in the commit.

## Checks

- Every step: `npm run check` and `npm test`, with `npm run build` where browser code changes.
- Steps 1 and 2 change no bout: the fingerprint with step 0's cases names no moved case, and step
  2's decoded data equals its source to the bit. Steps 3 and 4 move the cases of the data they
  touch, and their commits name them.
- Construction stays synchronous: `new Duel`, `enlist`, `createMind`, `createBody`'s sub-minds and
  the Dungeon's mid-run `wake()` (inside a world step) cannot await, so data is loaded before.
- A mind built without its data fails when built, naming the key and how to load it; it never runs
  with a substitute and never fails later, mid-bout.
- Every check runs in minutes; none is a battery read for its own sake.

## Done when

Every screen and Node harness loads only the data its minds read (step 1), and, once their trigger
comes, data ships packed at a precision measured per kind (steps 2 and 3). Afterwards, a CI check
of the built bundle (`.github/workflows/pages.yml`, after `npm run build`) holds the arena's startup
chunks under a set size, and new actions with data join through the store and the packer from the
start.
